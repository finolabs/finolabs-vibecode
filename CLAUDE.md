# finolabs-vibecode

Agent context for contributing to this repository. User-facing documentation is in `README.md`.

## What this repository is

One plugin with a skill set that gives AI coding agents a single engineering practice: routing of coding work, agent delegation, session hygiene, versioning, commit messages, code and security review gates, verification, and open source readiness. It also carries optional, consent-based usage metrics (hooks that record metadata only, and a local dashboard that `status` opens). It ships to Claude Code (`.claude-plugin/plugin.json`), Codex (`.codex-plugin/plugin.json`) and Antigravity (`.antigravity-plugin/plugin.json`) from one `skills/` folder. Keep each host's manifest in its own folder: a root `plugin.json` would be read by both Codex and Antigravity, whose schemas conflict.

## Conventions

- Every rule a skill states names its enforcer: a host setting, a hook, the review gate, or agent judgment. A rule enforced only by agent judgment is marked advisory and never promised as automatic.
- Compose before you build. Before adding a capability, look for a native host command or a trusted published skill that already does it: a known organization or author, an OSI license, active maintenance, readable instructions, no hidden network or credential behavior. Point to it by name with its source and install command, keep a fallback in our skill that holds the same quality bar without it, and credit it in the README. Our skills own routing, depth, delegation, gates and conventions.
- Every skill lives in `skills/<name>/SKILL.md`; the folder name equals the `name` field, and the name carries no prefix, so it stays short and easy to remember (owner decision, 11/11/2026, replacing the rule of 01/11/2026 that every name starts with `fnl-`; on Claude Code the plugin namespace `/finolabs-vibecode:<name>` avoids collisions). The older `fnl-<name>` aliases are retired (owner decision, 16/11/2026, replacing the rule of 11/11/2026 that each skill kept its older name as a thin, user-only alias in `skills/fnl-<name>/SKILL.md`): no `skills/fnl-*` folder ships, and a user types the current name (enforcer: `check-references.py` and `tests/test_manifests.py`). The agents lose the prefix too (`reviewer`, `security-reviewer`, `navigator`; owner decision, 16/11/2026); the `fnl-review` and `fnl-router` markers keep their names. Skills refer to each other by their current names.
- Each skill folder is self-contained, so it works when installed alone through skills.sh: nothing in it points outside its own folder. A file two skills need is copied into both (CI checks the copies match); a skill that needs another names it as a dependency.
- Each skill stays focused, with a trigger-rich `description` that leads with what the skill does and lists the distinct cases that should fire it. Disclose reference material into `references/` and executable helpers into `scripts/`.
- Host-specific facts (paths, commands, shims, allow-rules) belong in the host config described by `delegate`, never in skill bodies.
- Content is generic: no organization, customer or personal names, and no machine paths. Examples use synthetic names.
- All content is English.
- Usage metrics hold metadata only and stay off until the user consents. A new event field goes through `SCHEMA` in `scripts/fnl_metrics.py` and `docs/specs/usage-metrics.md`, never carries prompt, code, command text or paths, and updates `PRIVACY.md`. A hook never blocks a session: it exits 0 and fails closed, except for the scoped exceptions that say they may deny: the auto gate, the compaction stop, the heavy-job gate, the away question gate, the afk stop hook and the afk permission hook.
- One scoped exception to that hook rule (owner decision, 05/11/2026; design in `docs/specs/release-0.1.8.md`, package 7): the opt-in auto gate may deny the first file write in a repository when Delegation mode is `auto`, the user opted in during setup and no decision was recorded for that repository in the last 8 hours (and no denial was issued in that window). It allows on every other path and on any error, never blocks a session start, a stop or a read, and `FNL_AUTO_GATE=off` removes it. No hook other than the scoped exceptions that say they may deny blocks, and no code for the auto gate lands before this rule is merged.
- Second scoped exception (owner decision, 06/11/2026; design in a compaction-stop spec, written with the `PRIVACY.md` and `setup` changes before any code): the opt-in compaction stop on Antigravity, which has no host threshold. It is off unless the user turned it on in `setup` with a consent question of its own and a shown preview of the change, recorded in the canonical host config under the data root; if that cannot be resolved it is off. It is one hook in its own group in the user's own Antigravity hook configuration, never in the metrics group, installed and removed by a script that offers a dry run, keeps a backup and accepts only a bounded integer limit the user chose. On Antigravity's pre-invocation event only, at the first model call of a user turn (so the turn ends before the model runs and spends nothing), it may end that turn with one fixed message asking the user to run `/compact` or start a fresh session, when the transcript is over that limit. It never denies a tool call, a prompt, a session start or the user's own stop or quit, and never reads the transcript's content: it takes only the size of a regular file, not a symlink, inside the host's conversation folder. It stops at most once per conversation until the size has grown 10% beyond the size at the last stop; that mark is written atomically before the message, is reset when the transcript shrinks, is keyed by a hash of the conversation id in the data root's private state folder and holds no content. If the mark cannot be written or any check fails, it allows. It sends nothing anywhere. `--remove` takes it out and `FNL_COMPACT_STOP=off` disables it. No hook outside the scoped exceptions that say they may deny blocks, and no code for it lands before this rule is merged.
- The update check is the one network call the plugin makes on its own initiative (the quota probe and the context probe below run the user's own programs; the opt-in judge call in the fourth scoped exception below is the only other network call, made only when the coordinator or the user runs it): a detached worker makes a GET to the fixed public GitHub latest-release endpoint, sends nothing about the user, and stores only a timestamp and validated stable tag. It is on by default, separate from metrics consent; `FNL_UPDATE_CHECK=off` stops it. The session-start hook reads local state only, never waits for the worker, exits 0 and fails closed. See `docs/specs/update-check.md`.
- Scoped exception to the network rule above (owner decision, 05/11/2026; this text governs, and `docs/specs/release-0.1.8.md` package 13 may only narrow it): the opt-in quota probe. The data root below is the plugin's data folder, `~/.finolabs/vibecode/` by default.
  - Opt-in: off by default; it runs only when the user turned it on in setup and the host config in the data root records it, read only from that canonical file. If the data root cannot be resolved, or its pointer exists and is invalid, the probe is off.
  - Cadence (owner decision, 07/11/2026, replacing the 4-hour timer; design in `docs/specs/quota-on-demand.md`): no timer, and no hook starts a reading. A reading starts only when the coordinator is about to route a delegation and a candidate family's cached reading is older than 15 minutes, by running the plugin's `quota_probe.py read` command for that family, or when the user runs that command; at most one new reading per family per 15 minutes, a successful reading is not repeated within 15 minutes whatever age a caller passes (a lower `--max-age-minutes` is raised to 15), a failed run retried no sooner than 30 minutes later and a reply of an unexpected shape no sooner than 24 hours later. One reading runs at a time (a single in-flight marker); the command waits for its own run (one command per install of the family, each within the 30-second limit) and never starts a detached worker.
  - Hook: one hook entry in the Claude Code manifest only, for the `StopFailure` event, may record that Claude Code hit a rate limit, only when the event's `error` is exactly `rate_limit` and the probe is on in the canonical host config: the family and the time, nothing else, in the private state folder (no-follow, owner-checked, locked, atomic, input capped; any failure writes nothing). It starts no process and sends nothing. The marker is advisory: a repository can influence the error, so a newer successful reading of that family overrides it, it never excludes more than the family from routing offers, and the user's statement wins. The coordinator treats a marker as out of quota until the family's cached reset time when that lies within five hours after the marker, else for one hour after the marker. Every other hook only reads the cache.
  - Commands: only these commands of the user's own programs: `agy -p /usage --output-format json`; `claude -p "/usage" --output-format json` once for the default install and once per config folder the user listed (each absolute, owned by the user, not a symlink, not group- or world-writable and outside every git work tree, at most four in all, cached under the user's own labels; `CLAUDE_CONFIG_DIR` is set explicitly to each listed folder and left unset for the default install, whose folder and login the program resolves itself); and `codex app-server` limited to the `initialize` and `initialized` messages and the `account/rateLimits/read` request, ignoring every request the server sends.
  - Execution: each executable is resolved once at setup to an owner-checked absolute path the user confirmed, run with a fixed argv, no shell, an allowlisted environment, a neutral empty working folder, a 30-second limit with its whole process group killed, and a 64 KiB output cap. An executable inside a git work tree is refused, except under the Homebrew prefix (owner decision, 07/11/2026): the only git work tree allowed is the one rooted at exactly `/opt/homebrew`, so a nested repository (a tap, a clone) stays refused; the resolved target and any interpreter must lie inside that prefix, with no symlink leaving it; every component from the prefix to the file is owned by the user and not world-writable, and may be group-writable only when its group is `admin`; the preview shows the path for the user to confirm.
  - Data: the cache, the single in-flight marker, the rate-limit markers and the backoff times live in the data root's private state folder, never in a location a repository can redirect; the plugin stores only group names, windows, remaining fractions, reset times, the source, the time of the reading, the next allowed attempt and error class, the family and time of a rate-limit marker, and the user's own labels.
  - Network: those programs contact their providers with the user's own accounts; the plugin makes no network call and sends nothing about the user. `FNL_QUOTA_PROBE=off` stops the probe. No other command is run, no other network call is added beyond the scoped exceptions in this list, and no code for the probe lands before this rule is merged.

Failure: a timeout, a refusal status (401, 429), a missing key, a DNS or TLS failure, or a reply that does not validate (capped, closed schema) ends the call; the fallback is the small host model and the report says so, never silence. A call count per run is capped by `judge.py` as the spend guard. TypeSafe is the organization-approved data processor named in the owner's user-scope instructions; the plugin sends nothing about the user beyond the payload. `PRIVACY.md` (section "Judge") and the spec carry this text from the pull request that records this rule, and the `setup` consent text lands in the same pull request as the code or before it. `FNL_JUDGE=off` stops the call. ## Reviews

Pull requests follow `review-gate` "Pull requests"; reviewers may post their review comments on them. Pull requests may take the low-risk lane of `review-gate`. The lane covers changelog and root-document edits, manifest version bumps (the three plugin manifests' top-level `"version"`, such as the post-release bump to the next `-dev` version) and, by owner decision of 15/11/2026, a post-release record: the one `Status:` line of a `docs/specs/release-X.Y.Z.md` record changed from its prepared form to `released; tagged vX.Y.Z on YYYY-MM-DD; ...`, with only that release's row in `docs/specs/index.md` changed the same way; and, by owner decision of 17/11/2026, a catalog pin: a plugin catalog (`.claude-plugin/marketplace.json`, `.agents/plugins/marketplace.json`) whose only changes are existing entries' `source.ref`, moved to a release tag `vX.Y.Z`, and their descriptions; any other docs change stays outside the lane (enforcer: `merge_check.py --lane`).

Standing relay (owner, 02/11/2026): when one model family wrote a pull request, a code review by another model family that cannot post may be posted unchanged by the coordinator, with a second line naming the reviewer, who relayed it and this record. While an away lease is live in `open` mode, or in `strict` mode with Merge yes, the same standing relay covers a security review by another model family (owner, 15/11/2026: the lease's Merge answer already delegates reviews and merges; owner, 17/11/2026: an `open` lease delegates them too). In every other case, including a `strict` lease with Merge no, security reviews and every other relay still need the owner's approval per pull request.

Same-family security fallback (owner decision, 17/11/2026): outside an away lease, a security review by the pull request author's own model family counts without the owner's approval for that pull request only when the canonical host config records `- Same-family security fallback: yes (YYYY-MM-DD)` under `## Reviews` (asked in `setup` with its own neutral question and a preview), every other present review family is positively out of quota by the evidence the lease fallback uses, each marker's second line starts with the exact fallback reviewer line, two models of the family approve each kind when an enforcer script or instruction file changed, and the coordinator discloses the fallback on the pull request; the merge itself still waits for the owner's go (enforcer: `merge_check.py --independent --fallback-family`). Without that line, or with `no`, a same-family security review outside a lease still needs the owner's yes per pull request. The record covers no relay.

## Versions

`.claude-plugin/plugin.json` is the single source of truth for the version; `.codex-plugin/plugin.json` and `.antigravity-plugin/plugin.json` must match it. Follow `skills/versioning/SKILL.md` for bumps, the changelog and tags. Record every change to the public surface under `Unreleased` in `CHANGELOG.md`.

Docs that describe the product (owner decision, 17/11/2026): a pull request that changes what a user sees or does (a skill's behavior, a setup question, a hook, a command, an upgrade step) updates, in the same pull request, every one of these that the change touches: `README.md` (skill and setup tables, the release section, alt text), `skills/help/references/skills/<name>.md` for each affected skill, `skills/help/references/map.md`, `tips.md` and `troubleshooting.md`, `skills/setup/references/check.md` (what Check reports and which hooks run automatically), `skills/update/references/upgrades.json` (a note when the user must or may act), `PRIVACY.md`, `docs/how-it-compares.md` and the `docs/diagrams/` sources. Before a release, the drift review in `docs/specs/release-X.Y.Z.md` walks this whole list for every merged pull request, one row per surface, not only the ones the last record listed (enforcer: review gate and agent judgment, advisory).

## Checks before committing

- `claude plugin validate .` passes.
- A changed `description` gets a trigger check: a representative prompt fires the skill, and an unrelated prompt does not.
- `skills/open-source-review/SKILL.md` stays green for this repository.
- `python3 scripts/select_tests.py --base origin/main` lists the test modules the change touches (it prints them two per command and sees tracked files changed since the merge base, not untracked files); run them, at most two per command, and `python3 scripts/check-references.py .` passes; a `no test names: <path>` line means no test covers that file, so say so instead of reporting it as tested. The full suite (`python3 -m unittest discover -s tests`) runs in CI and before a release tag (owner decision, 17/11/2026).
