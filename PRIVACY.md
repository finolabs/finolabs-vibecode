# Privacy

`finolabs-vibecode` is a set of Agent Skills: Markdown instructions plus small local Python scripts. It has no server. Its network calls are the update check described below and, only if you choose Jev as your judge in `setup`, the judge call to TypeSafe described under "Judge" below; it sends nothing else about you or your sessions. If you choose, it records usage metadata on your machine so you can see how the practice performs; that record never leaves the machine, and it is off until you consent.

The agent scan script itself uses no network and runs `--version` only on three fixed executables (`claude`, `codex`, `agy`) without a shell and reads `host.md`; it stores nothing outside `host.md`.

Setup may write the user's own host compaction setting only after a previewed yes, keeping a private local plan and local backups; no data leaves the machine.

## Compaction handover

`<data root>/state/handover/<sha256(session id)[:16]>.md` is a local handover file: the user's own text, written by their agent (goal, decisions, work in progress and next action). `handover_state.py` stores at most 8 KiB as UTF-8, atomically, mode 0600 in a 0700 folder. At most 20 files are kept, with the oldest by modification time removed first. It has a 24-hour read lifetime: expired files are not read or re-injected, but may remain on disk until replaced, evicted or deleted by the user. The text is never sent by the storage or steward scripts and never enters metrics; the optional repository code is not stored. Safe text is re-injected locally into the same session on source `compact`, where the host's conversation policy below applies. Unsafe files or storage disable this feature silently. Claude Code vendor hooks/context-window docs and Codex 0.167.0 hooks docs plus pinned `rust-v0.167.0` source (07/11/2026) document SessionStart `source: compact` delivery on both hosts; live plugin delivery/order remains unverified. Claude Code PreCompact stdout feeds summary instructions; on Codex a plain-text reminder does not reach the model. See the [steward spec](docs/specs/compaction-steward.md) for sources and the advisory write-before-compaction procedure.

## Compaction stop

The optional Antigravity stop records `Enabled: yes` and the user-chosen `Limit bytes` in `## Compaction stop` in canonical `<data root>/host.md`. Setup stores a private digest-bound preview in `state/compact-stop-setup/preview.json` for at most 60 minutes of validity; it holds the limit, target and command paths, file hashes, modes, backup name and creation time, and is deleted after apply. The user's hooks file gets only the `finolabs-vibecode-compact-stop` group; a timestamped local backup preserves the previous bytes, is created with mode 0600 and narrowed to the previous mode & 0o600. Nothing is added to metrics.

`<data root>/state/compact-stop/<sha256(conversationId)[:16]>.json` holds only the integer transcript size at the last stop, mode 0600 in a 0700 folder. At most 200 marks are kept, oldest by modification time removed on write, excluding the current conversation's mark; shrink resets a mark. The hook reads the `## Compaction stop` section of the canonical host config and only the size of a regular, non-symlink transcript inside the account's Antigravity conversation folder, never its content. It sends nothing anywhere. `FNL_COMPACT_STOP=off` disables it; previewed removal deletes the hook group and sets `Enabled: no`, leaving marks and backups local until the user deletes them. Any failed check or mark write allows the turn. Antigravity vendor hooks docs through 1.5.3 (07/11/2026) confirm the user-level hooks file; live delivery and the interactive TUI remain unverified, as does whether `invocationNum` resets per user turn. See the [stop spec](docs/specs/compaction-stop.md) for sources and the fixed-message limitation.

## Agent snapshot

The dashboard's process snapshot is off by default. It runs only with recorded metrics consent and a separate setup opt-in in `## Agent snapshot` in canonical `<data root>/host.md`; if that file or the data root cannot be resolved safely, it is off. `FNL_AGENT_SNAPSHOT=off` disables collection, and setup can record `off` again. Environment overrides cannot grant consent.

During a dashboard refresh it may run the root-owned system `ps` with fixed arguments, no shell, only `PATH=/usr/bin:/bin` and `LC_ALL=C`, an empty temporary working folder, a two-second process-group limit and a 256 KiB output cap. It reads the current user's process names and elapsed times. macOS `comm` can be a full path; only its last component is compared, and the path is discarded. Only exact `claude`, `codex` and `agy` names become roots; exact `Claude`, `Codex` and `Antigravity` names contribute app counts. Descendant names are reduced to a fixed list or `other`, to depth six and at most 500 descendants per root.

It keeps only fixed family names, counts, elapsed seconds and the snapshot time, with a fixed reason on failure. It never keeps arguments, paths, environment values or user-chosen names, and never reads working folders or attributes processes to repositories. The machine-wide snapshot cannot distinguish a sub-agent from a session or list desktop app sessions. A process can adopt one of these names; family-level ledger mismatch flags do not prove a process's identity or liveness.

The `running` block in the dashboard's local `data.js` holds that snapshot beside the ledger's open dispatch labels, start times, budget, age and an unverified liveness marker. It is overwritten on refresh, reused for at most ten seconds between readings, removed by `status purge`, and never appended to the events files. No snapshot history or separate snapshot cache is kept. The page reloads this file; it does not run `ps`. Nothing is sent anywhere.

`refresh.py` also rebuilds `running.live` from existing consented usage events: distinct sessions with activity
in the last 15 minutes, by the fixed Claude/Codex/Antigravity families, capped at 99 per family, plus
`window_minutes: 15`. Session ids are transient deduplication keys and are not stored in this block.
These are recent activity counts, not process counts or an inventory of open sessions; an idle session
falls out of the window. `running.quota` holds up to eight cached pools per family, each with a pool
`name` (including a recognised window), `remaining_fraction`, `resets`, `measured` and `unverified`.
Pool names are at most 80 characters before a fixed window suffix; controls are rejected. The reset
and measurement times are validated timestamps or a missing reset. Quota data older than eight hours
is unverified. Empty families retain placeholders. These fields stay in overwritten `data.js`, never
usage events; purge removes them. The refresh builders enforce these bounds and shapes.

## Parallel capacity

`parallel_slots.py` reads the repository's approved total (1–32, default 3 when never configured, unknown when an approved settings file broke), optional per-family caps and open ledger starts. It writes nothing. Refresh projects `running.parallel_limit`, `running.family_slots` and `running.parallel_source` into overwritten local `data.js`; these are fixed family names, bounded counts/caps and a closed source word, never event fields. Purge removes the dashboard copy and leaves host config/ledger intact. Checks are advisory snapshots, not reservations; ledger starts do not enforce caps. See the [parallel-slots contract](docs/specs/parallel-instances.md).

## Project settings

Since 0.2.5 a repository's settings (`ledger`, `tasks`, `parallel`, `parallel-caps`, the display
`label` and the optional `autopilot` object: the repository's own away choices for task choice, push and pull
requests, merge, trusted authors and extra top-level code folders, which `autopilot.py check` reads in memory and never
stores) live in that repository's own folder: `settings.json` in `.finolabs/vibecode/` of the main
checkout (a linked worktree shares it only in the canonical, reciprocal, owner-checked layout
`<main>/.git/worktrees/<name>`). The file never leaves
the machine; the setter adds `.finolabs/` to the repository's `.git/info/exclude`, never to a tracked
`.gitignore`. `host.md` is never read or written for these settings, so it no longer lists one entry
per repository for every agent to read.

`project_progress.py settings --set <key>=<value>`, `settings --clear <key>` and `label --set <label>`,
run inside a repository, write that file (folders 0700, file 0600, atomic, under a file lock) and record
its SHA-256, the time and the SHA-256 of the main checkout path (never the path itself) in
`<data root>/state/settings-approved/<repository code>.json`; when the file
holds an `autopilot` object, that record also keeps the GitHub repository name of the checkout's origin
(`github.com/<owner>/<name>`, or null) the object was approved for, read from the repository's own Git
config. `ledger` and `tasks` require recorded metrics consent. The script splits `--set` on the first `=`
and prints only the key and changed/not changed, never the value. The one exception is the local preview
of the `autopilot` object (`--dry-run`, which writes nothing): it prints, on the user's own terminal, the
repository's main checkout and worktree paths, its code, its state, that GitHub repository name, the
object, the effective value of each key and a token that the apply repeats.

The file has a closed schema, `{"version": 1, ...}` with each key optional and each value a string
validated as before, except `autopilot`, a closed object of up to five keys (fixed words for task choice,
push and pull requests, merge and trusted authors, and `roots`, a list of 1–16 top-level folder names):
ledger names and labels of 1–40 ASCII letters, digits, spaces, dots, dashes or
underscores with a non-space character; task paths of 1–120 ASCII letters, digits, dots, dashes,
underscores or slashes, relative Markdown paths without empty, `.` or `..` components, outside
`specs/archive` and never an instruction file; `parallel` 1–32 and caps per family. The reader opens it
with no-follow descent, owner-checked and not writable by group or others, and uses it only while its
bytes match the approved digest. A file with no approval record, such as one supplied by a branch,
reads as unset. Once an approval exists, a file that is missing, unreadable, unsafe, invalid or edited
is broken: capacity reads unknown (`parallel_slots.py` exits 3), the ledger join reads unknown instead
of the folder name, the task file and label are off, and the session-start line and dashboard say the
settings need setup again. So a repository cannot raise `parallel`, relax an approved limit or redirect
`tasks`. Unset means the folder name for ledger, no task file, `parallel` 3 with no caps, and the
registered folder name as the label. `## Project settings`, `## Project labels` and the global
`Ledger project:`/`Task file:` lines left in `host.md` are never read; the user deletes them by hand.
Checkup flags an unmatched ledger mapping without disclosing project names; a machine-wide ledger
cannot establish repository association by itself.

The approved numeric `parallel` limit and family caps reach `data.js` and dashboard tooltips as bounded
counts, and the approved `label` is shown on the dashboard only for the repository the refresh runs in.
The `ledger` and `tasks` strings never reach `data.js`, tooltips, events or checkup output; they are
transient join/path inputs. The dashboard never reads `CLAUDE.md`, `AGENTS.md` or other recognised instruction
files for these facts. Purge leaves host config and the project settings files unchanged: they are the
user's own files. The settings reader/writer, checkup and refresh builders enforce these boundaries.

## Project progress

With recorded metrics consent, project progress is on by default when canonical `<data root>/host.md` can be read safely. An absent or ambiguous host config leaves it off. `Project progress: off` under `## Project progress`, the setup script's `off --yes` choice, or `FNL_PROGRESS=off` disables it. Repository config files cannot enable or redirect collection.

The refresh recognises local Spec Kit artefacts in `specs/<NNN-name>/`, then one-file work records, then repository indexes/status lines in `docs/specs/`, `docs/spec/` or `specs/`, release package tables and exact-project ledger runs. It also supports one optional checkbox file set in the repository's own approved settings file. It finds the root by walking at most 20 levels for `.git`, without running git. Every path component refuses symlinks; read descriptors must be regular, current-user-owned, nonblocking files. `tasks.md`/`spec.md` reads stop at 512 KiB, repository-state documents at 64 KiB. Other artefacts use regular-file presence only; `contracts/` must be a real directory. `specs/archive` is skipped. Listings stop at 200 entries; work-record selection counts entries across its candidate directories and retains at most 40 records, inspecting at most 64 KiB per file. It drops finished records first, then descending file names, and reports `work_records.skipped` (a lower bound when a listing or deadline interrupts inspection). Flat `specs/*.md` is read only when no `NNN-*` directory exists. Spec Kit stops at 60 features and 200 tasks each; repository state at 40 siblings plus an index, 40 items and 80 packages; ledger groups at 80 labels. All sources share one `ITIMER_REAL` one-second collect budget for reading, parsing and joins; timeout discards partial data. The shared reader caps lines at 4096 characters, ignores fenced headings and checkbox examples and opens directories with `O_DIRECTORY`, files with `O_NONBLOCK`, and every component with `O_NOFOLLOW`.

The `progress` block of local `data.js` stores only task ids, story tags, the priority number from a `User Story N (Pk)` heading (`P1` to `P9` only, otherwise absent), phase and feature numbers, checkbox states/counts, fixed agent families/outcomes, validated model tokens, short session ids and hosts, ledger ids, times, elapsed seconds, rework counts, review verdicts and the plugin manifest version. Heading text, task descriptions, file names, paths, links, session titles and ledger task wording are transient and discarded. Pipeline metadata adds fixed source/recognition/ledger-join enums, ordinals, stage/state enums (`done`, `active`, `todo`, `unknown`, `deferred`, `needs-attention`), counts, artefact-presence booleans, a closed status-keyword hint, closed `status_mark` tokens (`accepted`, `status-not-updated`), a work-record skipped count, review code/security counts and final-presence flags, package ordinals/states, and aggregate latest ledger-task outcomes. Work records expose only checkbox counts and numeric tags, stage presence and the closed Status state. Status wins over Tasks; all tasks checked while Status is in progress adds an amber “status not updated” mark. Evidence content is never kept. Status lines, index cells, links and package wording stay transient; no titles or filenames are stored. `unknown` means no status stated; artefacts never imply review approval. The other kept values are the priority number, the user's optional project label, and the repository folder name registered by running status. `project_progress.py label --set <label>`, run inside the repository, writes the `label` key of that repository's own settings file (see Project settings). Labels contain 1 to 40 ASCII letters, digits, spaces, dots, dashes or underscores, with at least one non-space character. An explicit label always wins over a registered name; repositories with neither name are not shown. Labels are local, never sent anywhere, and the ledger project name is never reused as a display label. The ledger fields read are project name and task label for exact matching, id, agent, model, start, finish, outcome and rework rounds. The repository's approved `ledger` setting overrides the folder name for the match; when an approved settings file broke, no runs are matched and the ledger join reads unknown. The project name itself is not kept in progress. The usage event `dispatch` is a delegated run id or null, and sessions link through that exact id; a `task` event can link a manual session when its id identifies a single feature. Duplicate task ids across features stay unlinked.

Running `status` inside a repository is the act that names it as a project of this plugin. Only after the user ran status there, with recorded metrics consent, `run --register-here` keeps the repository folder name locally in `<data root>/state/projects.json`, keyed by its 8-hex repository code. Hook-started refreshes never register names. The folder basename is sanitised to ASCII letters, digits, spaces, dots, dashes and underscores (other characters become `-`), trimmed and limited to 40 characters; empty names are skipped. This closed map has at most 50 entries and is atomically written with mode 0600 in a private folder under a file lock. Names are never sent anywhere. Remove registered names by running `status purge` or deleting `state/projects.json`; explicit labels in each repository's own settings file remain separately configured. A repository the user never ran status in and never explicitly labelled is not shown as a project.

Every refresh replaces the current repository snapshot, keyed by its existing short repository code, and retains up to four other last-written snapshots. The page shows one compact line per named active repository, with unfinished spec/story/task detail in a disclosure closed by default. Finished features and stories are hidden in that detail; all old data tables remain available under "show the data as tables". It is deleted by purge and never appended to events files. The overwritten `progress.active` list keeps only named repositories, newest first, up to 12, and counts distinct sessions with at least one event in the last 24 hours (a rolling window, including across midnight). It keeps the same repository codes and counts the events already hold, resolved local labels, closed host names, latest event times and task completion percentages when available; session ids are used only to deduplicate the counts and are not kept in the activity list. It is rebuilt from existing events each refresh, never carried over, and removed by purge. There is no progress history or separate task cache. The page uses textContent, never interprets task data as instructions, and sends nothing. Done means the box is ticked; task receipts never drive task selection or any gate. Running now is a machine-wide process count, not an identified count of sessions in this project. A one-time page notice and a once-per-version session-start line announce the change; only their delivery flags are stored in `<data root>/state/notices.json`.

## Where your data goes

The data folder can be relocated through `setup`; the fixed pointer `~/.finolabs/vibecode/root.json` contains its absolute `root` path and a random `id` matching the new folder's `.root-id`.

The skills run inside a host agent such as Claude Code or Codex, which processes your conversation under its provider's policy. When you follow the delegation skills and delegate work to another agent (for example Codex or Antigravity), the brief, the files that agent reads and anything it produces are processed by that agent's provider under that provider's terms. Delegate only work over files you are allowed to share with that provider.

Only after separate instruction-check consent, `setup` Check may supply screened instruction-file lines to a small host model. This is outside `judge.py`'s four outbound sites, so choosing Jev does not send these lines to TypeSafe. `checkup.py --judge-payload` only prepares local line text: size capped, secret or machine-path lines dropped, nothing from a file with a secret finding, and never `.bak-*` backups, scan results or `CLAUDE.local.md`. Supplying that packet to a model is an advisory agent action under the host provider's policy; the read-only script makes no network call.

## Verification receipts

`verify_claim.py` runs the targeted commands approved in the brief and prints their evidence locally. Semantic checks use the configured judge described under "Judge" below. Host judging makes no network call from the script; evidence supplied to a host model follows that host's provider policy.

`record.py verify` stores `<data root>/state/verification/<dispatch id>.json`, mode 0600 in a 0700 folder. It holds the dispatch id, head, SHA-256 checkout identity (`checkout_id`), test and mechanical results, optional SHA-256 evidence-packet digest (`evidence_id`), and criterion identifiers, answers, sources and fallback flags. It stores no questions, commands, evidence text, test output or paths, and never enters usage events. Receipts remain until replaced or manually deleted; metrics purge does not remove them. The dashboard copies only per-agent accepted-without-verification counts from the ledger into its overwritten local `data.js`; it sends nothing and purge removes that dashboard copy.

When requested, `verify_claim.py --requests-out` also writes an owner-only local packet containing the questions and evidence for host completion. This is a private work artifact at the caller's chosen path, outside plugin state and metrics; retain and delete it with the task's other private artifacts. It can contain source and test output. The script sends none of that packet automatically to a host model.

## Restore points

Only when requested, `restore-point create` stores a working-tree snapshot in the repository's git object store under `refs/finolabs/restore/`. It includes tracked files and non-ignored untracked files, including `.env` if it is not ignored; these are file contents, not usage metadata. The helper makes no network call, but Git can run repository-configured filters. The private ref does not isolate the objects from someone who can read or copy that repository. Never push `refs/finolabs/*`; mirror clones and bundles can carry them. Restore requires a preview and approval, makes a `pre-restore` snapshot and keeps extra current files. These objects/refs are outside the data root and metrics purge, with no automatic retention expiry. See the [procedure and partial-restore limits](skills/restore-point/SKILL.md).

## Update check

The update check is **on by default**, separate from usage metrics and their consent. At startup on Claude Code and Codex, a detached worker makes one HTTPS GET to `https://api.github.com/repos/finolabs/finolabs-vibecode/releases/latest` when the cache is missing or at least 24 hours old. It uses only the generic User-Agent `finolabs-vibecode-update-check`: no request body, credentials, cookies, username, machine, repository, session, installed version, prompts, code, paths or usage events. It sends nothing about the user. GitHub necessarily sees your connection's source IP. There are no redirects, proxies or retries.

Set `FNL_UPDATE_CHECK=off` in your host's environment to stop requests and notices. A “never ask” choice suppresses notices while checking continues. A “skip this version” choice suppresses only that version. The checker never updates the plugin; `update` asks for your clear yes before a native host update. Host-native updates have their own network behavior.

The resolved data root's `state/` folder (normally `~/.finolabs/vibecode/state/`, without environment overrides) holds `update-check.json` with only `checked_at` (Unix timestamp) and `tag` (validated stable release tag), plus `update-state.json` with only `skipped` (versions), `never_ask` (boolean) and, while the user holds a version, `pinned` (a version string), and `onboard.json` with only `last_seen` (a version) and `skipped` (upgrade-note ids), nothing else. All are mode `0600`. No response body or error text is stored. These files are separate from usage events and metrics consent; turning metrics off or purging them does not stop the update check. Turning the update check off leaves existing files unchanged.

The first stable release carrying the checker gives no notice of itself: older installs have no checker, and an equal version produces no notice. Missing caches initialize silently; failures print nothing and never stop a session. See the [update-check spec](docs/specs/update-check.md) for the exact data and limits.

## Quota probe

For the quota probe, the plugin itself makes no network call. The user's own `agy`, `claude` and `codex` programs contact their providers with the user's own accounts; the plugin sends nothing about the user. This is separate from the update check above.

The probe stays off until setup records the dated opt-in in the canonical `<data root>/host.md`, under `## Quota probe`. That section lists selected agents, confirmed absolute executable and interpreter paths, and labelled Claude config folders. For the default Claude Code install, `CLAUDE_CONFIG_DIR` is left unset so the program resolves its own folder and login; it is set only to config folders the user listed. Each Claude install starts with its usual configuration, including hooks, plugins and servers. `FNL_QUOTA_PROBE=off` stops probing; metrics consent neither enables nor disables it.

`<data root>/state/quota/quota.json` stores, per agent and user-chosen label, only `measured`, `source` and groups with `name`, `window`, `remaining_fraction` and `reset_time`. It contains no account, identity, email, path, plan, credit or token fields. `backoff.json` stores only `retry_after` and an error class per agent and label; `inflight.json` holds a per-run random token and UTC start time during a synchronous reading. `limits.json` stores only the family and time of a rate-limit marker from the Claude Code StopFailure hook, only for exact `error: rate_limit` with probing on; no provider text is stored. This advisory marker expires at the earliest reset among family pools below 10% remaining if future and within five hours after the marker, otherwise one hour after the marker, never over five hours; a newer successful reading overrides it. Files are private (0600) in a private folder (0700). No raw program output is saved. The coordinator requests a reading before delegation with `quota_probe.py read --family <f>`; hooks start no quota reading. Successful readings wait at least 15 minutes; failures wait at least 30 minutes, changed formats 24 hours, and Claude replies treated as prompts 7 days. The commands run from an empty private folder under `<data root>/tmp/`, removed afterwards. Turning probing off leaves cached files unchanged; delete the quota state to clear it. The child environment disables metrics and the update check. Claude Code [vendor hooks docs](https://code.claude.com/docs/en/hooks.md), researched 07/11/2026, verify StopFailure's exact `error: rate_limit` contract, no token counts and ignored output/exit code; the live payload/plugin delivery, other Claude text formats and Windows remain unverified.

## Context reading

Only when the user configures a Claude Code or Antigravity status-line command, `context_snapshot.py record` receives its JSON on stdin (64 KiB cap). It never reads a transcript, starts a process or uses the network. Used tokens are the last main-conversation response's input, cache-creation and cache-read tokens; output tokens and the host's reported percentage are excluded. Only `used`, `window`, whole `percent`, UTC `measured`, short sanitized host `version` (or `unknown`) and explicit `host` (`claude` or `antigravity`) enter `<data root>/state/context/<sha256(session id)[:16]>.json`. Claude uses the session id only for the filename hash; Antigravity uses `sha256("antigravity:" + conversation_id)[:16]` instead, separating the two hosts. The conversation id is also hashed only; no path, transcript path, session id, content or raw payload is stored there. Files are 0600 in a 0700 folder, atomically replaced with no-follow and owner checks, independent of metrics consent, and never enter events or receipts. At most 20 snapshots remain, oldest mtime first; null or invalid usage removes that session's old snapshot. Other invalid or oversized payloads write nothing. Reads refuse after one hour by default (caller may explicitly choose up to 24 hours); expiry does not delete files. Delete the context folder to clear readings; removing the status line stops future recording but leaves existing snapshots.

SessionStart reads only the starting session's fresh snapshot and prints percent, window and age, on every start source except `compact`. `read --latest` selects the newest snapshot by mtime and may refer to another parallel session; it conveys no session identity. The manual recipe for an existing user-owned status line temporarily spools its stdin JSON in a private `mktemp` file, feeds the recorder before the original command, and removes the file with an EXIT trap; it is not stored as plugin telemetry. Antigravity is covered by the recorder; the SessionStart Context line remains Claude-only. Codex is not covered: vendor docs and pinned source for 0.167.0 (07/11/2026) expose app-server context telemetry and built-in TUI items, with no external JSON status-line command. See the [snapshot spec](docs/specs/context-snapshot.md) for sources and limits.

`statusline_setup.py` changes settings only after an approved full preview digest and explicit yes. It keeps a private preview in `<data root>/state/statusline/preview.json`, containing target settings paths, original file hashes/modes, backup names, the proposed status-line command, removal choice, data-root path and creation time. Apply accepts it only within 60 minutes and removes it after success; an expired preview remains until replaced or manually deleted. Adjacent `settings.json.bak-YYYYMMDD[-N]` backups contain the previous settings and remain until the user deletes them; backups and every settings file the writer rewrites end up with mode 0600. An existing status line gets only a printed recipe, with no new plan or settings write. Removal only deletes the exact configured recorder command. The preview and settings backups are local configuration artifacts, never events or receipts, and are not removed by metrics purge. Installed-host delivery and composition with an existing status line remain unverified.

## Context probe

Only when the coordinator or you run `context_snapshot.py probe` (never from a hook, a timer or a worker), it runs your own `claude` or `codex` once, only the program you confirmed in the quota probe setup, to read the current session's context size: Claude Code's local `/context` command on a forked, unsaved copy of the session, which runs no model turn, or, for Codex, an app-server that first reads the thread's state and goal and resumes your own thread only when it is idle or not loaded and has no goal, sending no turn. Those programs contact their providers with your own account, as any start of them does, and MCP servers you configured for them may start and stop with them; the plugin sends nothing. It writes the same snapshot fields as the status-line recorder (used and window tokens, whole percent, time, short sanitized version, host) under a hashed session id in the private context folder, never the category breakdown, any content, the raw session id or a path.

To let the agent pass its own session id, the session-start hook prints one validated `Session id:` line. That id enters the host's model context, which the host may keep; the plugin does not store it as plain text in snapshots or events. Antigravity is not covered. `FNL_CONTEXT_PROBE=off` stops the probe. Design: `docs/specs/context-probe.md`.

## Compaction nudge

On Claude Code, on by default, one `UserPromptSubmit` hook tells the agent when the session nears the compaction threshold, so it saves a handover and writes back decisions before the host compacts. To measure, it reads only the integer token counts (`usage`: input, cache creation, cache read and output tokens) of the latest assistant entry in the last 256 KiB of the session's own transcript file, which it opens only when it is a regular file, not a symlink, inside the host's `projects` folder; it never reads, keeps, logs or sends any other field or any of your conversation. It reads `autoCompactEnabled` and `autoCompactWindow` from your Claude Code settings files and the integer values of `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` and `DISABLE_AUTO_COMPACT` from the environment, nothing else. At 80% and again at 90% of the threshold it prints one fixed line with a whole percent into the agent's context. It stores one integer per session (the last band it reported) under a hash of the session id in the data root's private state folder, records no metrics event, never blocks anything and sends nothing anywhere. `FNL_COMPACT_NUDGE=off` turns it off. Codex and Antigravity are not covered. Design: `docs/specs/compaction-nudge.md`.

## Repository checks

`/setup add checks` stores a repository's check list, as argument arrays you approved, in that repository's own `.finolabs/vibecode/checks.json` (in the main checkout, shared by its linked worktrees; folders 0700, file 0600), and adds the line `.finolabs/` to the repository's `.git/info/exclude`, never to a tracked `.gitignore`.
It records the SHA-256 of the approved file and the time in `<data root>/state/checks-approved/<repository code>.json`; a file that differs from it, or has none, runs nothing.
Replacing the list keeps the previous file beside it as `checks.json.bak-<date>`. Undo is `checks_setup.py remove` for this repository: it deletes the file and its approved digest and leaves the backups.
A list saved with 0.2.4 under `## Checks` in canonical `<data root>/host.md` is no longer read, and the plugin neither reads nor changes that section; delete it by hand after you save the list again. Running the checks runs the repository's own code on your machine; the plugin sends nothing anywhere.

The opt-in local receipt is `<data root>/state/checks-receipts/<repository code>.json`, mode 0600 in a 0700 folder. It holds the repository code, the head, the digest of the check list and the time, and no command text or output. An empty `<repository code>.lock` beside it allows one full run at a time. To stop new receipts, run `checks_setup.py receipt off`, approve its preview and run `checks_setup.py apply --yes --digest <Digest>`. Turning the mode off leaves an existing receipt and lock file on disk; the next full run removes the earlier receipt.

`checks.py usage` reads a file you produced and makes no network call. The optional workflow writer creates one file in your repository and never commits or pushes it; a workflow you commit runs your repository's code on your CI provider, under that provider's policy. When it replaces a workflow, the old file is kept in `<data root>/state/checks-ci/backups/`.

Previews are saved before you approve them, in `<data root>/state/checks-setup/preview.json`, `state/checks-hook/preview.json` and `state/checks-ci/preview.json`. They hold the proposed argument arrays, the repository, hooks and data-root paths and the generated hook or workflow text. A successful apply deletes the preview and a new preview replaces it; a preview can be applied for 60 minutes, and an expired one stays on disk until one of those happens. Replacing or removing a pre-push hook keeps the old hook as `pre-push.bak-<date>` in Git's hooks folder, shared by every worktree of the repository, with the old hook's own mode (at most 0755), not in the private state folder.

## What the plugin stores on your machine

- With the auto gate enabled, `<data root>/state/auto-gate/<key>.json`: a repository key in the filename (the first 12 hex characters of SHA-256 of the normalized repository root), `decision` (`handoff` or `keep`) with `decided`, and optionally `denied`, both ISO timestamps. Before a decision, the file can contain only `denied`. The script stores no path, task label or session id and sends nothing over the network. This local-only state is independent of usage metrics. The account home comes from the operating system, never `HOME`, `FNL_STATE_DIR` or `XDG_STATE_HOME`. The hook uses an 8-hour window; stale state can be replaced on the next write, not automatically purged. Turning the gate off leaves existing files unchanged; delete them to clear the state.

- `<data root>/state/review-posting/post-<random>/body.md`: a private review draft of at most 64 KiB (file mode `0600`, folder mode `0700`). After a post is observed successfully, the wrapper deletes the draft and its run folder. Failed or unobserved posts retain the draft for manual inspection and deletion. Preparing a draft sends nothing; an explicitly authorized post sends its contents to the checkout's GitHub repository. Public repository comments are public.

- `<data root>/ledger.jsonl` (no environment override): one line per delegated run with a short task label, the agent, the model, timings, the outcome and, when supplied for review routing, the implementation head SHA. Verification adds the checkout identity hash to starts and the verified head and exception flag to accepted finishes; an unverified exception stores only the SHA-256 reason digest (`reason_id`) and `accept_unverified`, never its reason text; a `--reason` given with any other outcome is kept the same way. An accepted review dispatch may add the head it reviewed (`reviewed_head`) and `review_posted`; the review comment URL is checked by pattern and never stored or fetched. When the coordinator supplies them, a start also records the install name (`install`, such as `claudework`), the type of work from a closed list (`work_type`), the numeric level (`level`) and the rank of the chosen agent in the routing query's answer (`pick_rank`); these stay in the local ledger and are never usage event fields. When a dispatch runs through `delegate_env.py` with `FNL_DISPATCH_ID` set, the wrapper adds one `ended` line holding only that id, the time and the child's exit code, never command text, output or paths. It holds no prompts, code, secrets or personal data. Delete the file to clear it.
- Only after you consent in `setup`, through the plugin's hooks on Claude Code and Codex, and on Antigravity when you add its hook in setup: usage events in `<data root>/state/events-YYYY-MM.jsonl` (or under `FNL_STATE_DIR`, or in the older `${XDG_STATE_HOME:-~/.local/state}/finolabs-vibecode` folder where it already exists), one line per event. A line holds a time, a session id, a short code derived from the repository path, and a few fixed fields: the name of one of this plugin's skills or `fnl-` agents that ran, the coding router's depth, a review verdict with a pull request number, the number of tasks a coordinator kept with a fixed reason and who settled it, a task id (`task` event, only `id` of the form `T` plus one to four ASCII digits, nothing else), or the delegated run id (`dispatch`, the value of `FNL_DISPATCH_ID` or null, not a boolean). It never holds prompts, code, command text, file paths or review text. Judge receipts hold only `site`, `grader`, `result`, and `followed` from fixed enumerations; they never hold a question, an answer, a cost, a file name or a path. Consent always lives in `<data root>/state/consent.json` (the date and how long to keep events), ignoring environment overrides; an invalid root pointer disables consent. The events folder holds a marker file per session, an error counter with the class name of the latest error (never its text), and the dashboard (`dashboard.html`, its local `dashboard.js` and `data.js`), which `status` opens in your browser from your disk. Events older than the retention you chose (30, 90 or 365 days) are deleted at the start of a session, and `status purge` deletes them all at once. Set `FNL_METRICS=off`, or ask `status` to withdraw consent, to stop recording at any time; it asks you first, then runs `refresh.py consent --revoke --yes`. Task events are advisory dashboard data only and never drive task selection or a gate; any session can forge one. The events are best effort: they are read from tool calls and command text, so they can miss an action or count one that was only written out.
- `.finolabs/` in your repository (older versions used `.orchestration/`), when you follow `delegate` "Where files go": briefs, logs and handover notes that you or your agents write. The skill tells agents to keep this folder out of git.
- Canonical `<data root>/host.md` holds confirmed role families and the judge under `## Agent roles`, or, once you set the assignment matrix in `setup`, under `## Assignment matrix` together with each agent's task levels, types of work, model and roles (that section carries its own consent line and replaces the older sections; a damaged one is read as unset, never as the older one), and `## Review posting` holds only each family’s `yes`, `no` or `unverified` state and check date; these facts grant no posting rights, and SessionStart prints only fixed role and posting words.
- `## Setup features` in canonical `host.md` records only declined feature names with `declined`, separately from any consent, so a bare setup skips those offers while explicit `add <feature>` asks again; malformed records refuse updates without discarding foreign lines.
- The host config file you create from `skills/delegate/references/host-template.md` holds local machine facts; consent-bearing sections are read only from canonical `<data root>/host.md`.

## Reporting issues

Public issues and pull requests are visible to everyone. Remove credentials, personal data and private repository content from any transcript, brief or log before you post it. Report security problems privately as described in [SECURITY.md](SECURITY.md).

## Away decisions, only during a lease you start

While an away lease you started is active, the ledger records each decision made in your place: the time, the project, the lease's start time, which step decided (a rule, Jev, the advisor, or parked), the agent and model, the chosen option's number, the probability when Jev decided, the dispatch id and a short topic label. It holds no question or option text. On Claude Code one hook denies the question tool during the lease and adds a line with only the time and the lease's start time. A decision that goes to Jev or to another agent sends that provider the question, the options and the evidence the question needs; with a separate yes in `setup`, that evidence includes short excerpts of your own past decisions from your knowledge base and the host's memory, at most eight excerpts and 8 KB, each screened for secrets and machine paths. Without that yes no excerpt leaves your machine. The ledger also records whether you later kept or reversed each decision. `FNL_AWAY_GATE=off` disables the hook.

## Judge (TypeSafe), only if you choose it

If you choose Jev as the judge in `setup` (recorded as `Judge: jev` with its own consent line in `## Assignment matrix`, or as `judge: jev` in the older `## Agent roles` while no matrix exists) and set `TYPESAFE_API_KEY` in your environment, `judge.py` sends one HTTPS request per judgment to `https://api.typesafe.ai/v1/systemone` when the coordinator or you run it. The request holds only a bounded English question and the evidence the question needs (verification criteria with the supporting lines, a navigator question, an uncertain compaction boundary, a delegation grade); a field with a secret or machine-path hit makes the call refuse. The key is read only from the environment and is never printed, stored or passed on. TypeSafe processes the payload under your organization's agreement. The script makes no network call when the judge is the host model (the default), and `FNL_JUDGE=off` stops Jev calls; evidence supplied to a host model follows that provider’s conversation policy. The optional `typesafe-ai` skill supplies cookbooks and is outside the call path: `judge.py` uses the scoped Jev network exception with canonical opt-in and the user’s own API budget.

Each call uses a closed per-site schema and byte caps, verified TLS, no redirect or proxy, and at most 24 outbound attempts per process including failures. Unavailable Jev calls return an explicit host fallback; only validated replies count as Jev use. Host `yes` answers require a meaningful quote present in the supplied evidence; a quote check proves presence, and the coordinator decides support and acceptance. Judge validation remains labelled unvalidated pending independent cases. Cross-document criteria are split and their answers compared in code.

`record.py judge` can emit consent-gated usage metadata containing only fixed `site`, `grader`, `result` and `followed` words; no question, evidence, reply text or probability enters those events. Relay-specific receipts and dashboard counters remain unimplemented; no relay event is stored by the current scripts.

## Run hygiene

Log scanning and redaction are local; no scan data is sent anywhere. `ledger.py finish --log-path <log>`
scans a descriptor-checked regular file inside the private run-log folder before recording the run.
The ledger's `log_scan` is one of three fixed words: `no_findings`, `findings`, `not_scanned`, never `clean`.
It copies no log text and is not a usage-metrics field. Binary, unreadable, unsupported-control and over-8-MiB logs, or logs exceeding 250,000 pairs per scan pass, are `not_scanned`; 1,000 candidate hits instead produce a whole-input `match_limit` finding.
`log_scan.py show` prints only a located redacted view and refuses unsupported logs; scan output contains
fixed kinds, file ordinals and line numbers, plus safe variable names only, never values or value fragments.
Redaction requires a preview digest and `--yes`, refuses logs modified in the last 60 seconds and rechecks descriptor metadata before rename, and atomically replaces the
original without a backup; an idle open descriptor alone is not detected and a concurrent same-user write after the final check remains a race. Agents' own transcript stores remain untouched and may require owner cleanup;
provider copies cannot be undone. HOME remains reachable: the protection is environment-only for headless
command forms, excluding interactive, desktop-app sessions and in-session subagents. Private HOME is deferred.

## Autopilot lease and log

When you run autopilot's `start`, the plugin writes `state/autopilot/lease.json` and, as actions are classified or logged, `state/autopilot/log.jsonl` in the private state folder of the data root (folders 0700, files 0600; never in a repository). The lease holds a lease id, its start and end times, a hash of the setup it applied, and counters of runs, runtime minutes and actions per hour. The log holds, per entry, the time, a tier, a fixed kind word, task, run and pull request ids, and a note of at most 500 characters from which control characters, paths, command text and secret-looking values are removed. Command lines and file paths given to `check` are classified in memory and never stored. This is a local record kept apart from the usage metrics and their consent: it is never in the events, never sent anywhere by the plugin, entries older than 30 days are pruned when the log is written, and the file is capped at 8 MiB. `stop` deletes the lease; delete the folder to remove the log. The advisor and Jev calls of the full design are not part of this release.

When you run `pause`, the plugin writes `state/pause.json` in the same private state folder (folder 0700, file 0600; never in a repository). It holds a start time, a kind (`restart`, `shutdown` or `none`) and a deadline time, nothing else: no path, command or session text. `resume` deletes it, and a marker older than 24 hours is ignored. It is never in the events and is never sent anywhere by the plugin.
