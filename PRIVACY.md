# Privacy

`finolabs-vibecode` is a set of Agent Skills: Markdown instructions plus small local Python scripts. It has no server. Its only network call is the update check described below; it sends nothing about you or your sessions. If you choose, it records usage metadata on your machine so you can see how the practice performs; that record never leaves the machine, and it is off until you consent.

The agent scan script itself uses no network and runs `--version` only on three fixed executables (`claude`, `codex`, `agy`) without a shell and reads `host.md`; it stores nothing outside `host.md`.

Setup may write the user's own host compaction setting only after a previewed yes, keeping a private local plan and local backups; no data leaves the machine.

## Compaction handover

`<data root>/state/handover/<sha256(session id)[:16]>.md` is a local handover file: the user's own text, written by their agent (goal, decisions, work in progress and next action). `handover_state.py` stores at most 8 KiB as UTF-8, atomically, mode 0600 in a 0700 folder. At most 20 files are kept, with the oldest by modification time removed first. It has a 24-hour read lifetime: expired files are not read or re-injected, but may remain on disk until replaced, evicted or deleted by the user. The text is never sent by the storage or steward scripts and never enters metrics; the optional repository code is not stored. Safe text is re-injected locally into the same session on source `compact`, where the host's conversation policy below applies. Unsafe files or storage disable this feature silently. Hook delivery to the model remains unverified on every host.

## Compaction stop

The optional Antigravity stop records `Enabled: yes` and the user-chosen `Limit bytes` in `## Compaction stop` in canonical `<data root>/host.md`. Setup stores a private digest-bound preview in `state/compact-stop-setup/preview.json` for at most 60 minutes of validity; it holds the limit, target and command paths, file hashes, modes, backup name and creation time, and is deleted after apply. The user's hooks file gets only the `finolabs-vibecode-compact-stop` group; a timestamped local backup preserves the previous bytes, is created with mode 0600 and narrowed to the previous mode & 0o600. Nothing is added to metrics.

`<data root>/state/compact-stop/<sha256(conversationId)[:16]>.json` holds only the integer transcript size at the last stop, mode 0600 in a 0700 folder. At most 200 marks are kept, oldest by modification time removed on write, excluding the current conversation's mark; shrink resets a mark. The hook reads the `## Compaction stop` section of the canonical host config and only the size of a regular, non-symlink transcript inside the account's Antigravity conversation folder, never its content. It sends nothing anywhere. `FNL_COMPACT_STOP=off` disables it; previewed removal deletes the hook group and sets `Enabled: no`, leaving marks and backups local until the user deletes them. Any failed check or mark write allows the turn. User-level hook delivery and the interactive TUI remain unverified.

## Agent snapshot

The dashboard's process snapshot is off by default. It runs only with recorded metrics consent and a separate setup opt-in in `## Agent snapshot` in canonical `<data root>/host.md`; if that file or the data root cannot be resolved safely, it is off. `FNL_AGENT_SNAPSHOT=off` disables collection, and setup can record `off` again. Environment overrides cannot grant consent.

During a dashboard refresh it may run the root-owned system `ps` with fixed arguments, no shell, only `PATH=/usr/bin:/bin` and `LC_ALL=C`, an empty temporary working folder, a two-second process-group limit and a 256 KiB output cap. It reads the current user's process names and elapsed times. macOS `comm` can be a full path; only its last component is compared, and the path is discarded. Only exact `claude`, `codex` and `agy` names become roots; exact `Claude`, `Codex` and `Antigravity` names contribute app counts. Descendant names are reduced to a fixed list or `other`, to depth six and at most 500 descendants per root.

It keeps only fixed family names, counts, elapsed seconds and the snapshot time, with a fixed reason on failure. It never keeps arguments, paths, environment values or user-chosen names, and never reads working folders or attributes processes to repositories. The machine-wide snapshot cannot distinguish a sub-agent from a session or list desktop app sessions. A process can adopt one of these names; family-level ledger mismatch flags do not prove a process's identity or liveness.

The `running` block in the dashboard's local `data.js` holds that snapshot beside the ledger's open dispatch labels, start times, budget, age and an unverified liveness marker. It is overwritten on refresh, reused for at most ten seconds between readings, removed by `fnl-status purge`, and never appended to the events files. No snapshot history or separate snapshot cache is kept. The page reloads this file; it does not run `ps`. Nothing is sent anywhere.

## Project progress

With recorded metrics consent, project progress is on by default when canonical `<data root>/host.md` can be read safely. An absent or ambiguous host config leaves it off. `Project progress: off` under `## Project progress`, the setup script's `off --yes` choice, or `FNL_PROGRESS=off` disables it. Repository config files cannot enable or redirect collection.

The refresh reads local Spec Kit `specs/<NNN-name>/tasks.md` and the sibling `spec.md`, plus one optional `Task file: <relative path>` from that host section. It finds the repository by walking upward at most 20 levels for a `.git` entry, without running git. Every path component is opened without following symlinks and without blocking on a FIFO; final files must be regular, owned by the current user and at most 512 KiB. Folders under `specs/archive` are skipped and not counted. Listings stop at 200 entries, task and spec reads share the 20-file cap and output at 200 tasks per feature. Parsing and joins share a one-second wall-clock budget; an overrun discards the partial result with a fixed reason.

The `progress` block of local `data.js` stores only task ids, story tags, the priority number from a `User Story N (Pk)` heading (`P1` to `P9` only, otherwise absent), phase and feature numbers, checkbox states/counts, fixed agent families/outcomes, validated model tokens, short session ids and hosts, ledger ids, times, elapsed seconds, rework counts, review verdicts and the plugin manifest version. Heading text, task descriptions, file names, paths, links, session titles and ledger task wording are transient and discarded. The only new kept values are the priority number and the user's own optional project label. `project_progress.py label --set <label>`, run inside the repository, writes a repository-code-to-label entry under `## Project labels` in canonical host config. Labels contain 1 to 40 ASCII letters, digits, spaces, dots, dashes or underscores, with at least one non-space character; the page otherwise shows `repo <first four code characters>`. Labels are local, never sent anywhere, and the ledger project name is never reused as a display label. The ledger fields read are project name and task label for exact matching, id, agent, model, start, finish, outcome and rework rounds. A host `Ledger project: <name>` overrides the repository folder name for the match; the project name itself is not kept in progress. The usage event `dispatch` is a delegated run id or null, and sessions link through that exact id; a `task` event can link a manual session when its id identifies a single feature. Duplicate task ids across features stay unlinked.

Every refresh replaces the current repository snapshot, keyed by its existing short repository code, and retains up to four other last-written snapshots. The page draws unfinished work across those repositories; completed projects, features and stories are hidden, with counts and the full data equivalent in disclosures. It is deleted by purge and never appended to events files. There is no progress history or separate task cache. The page uses textContent, never interprets task data as instructions, and sends nothing. Done means the box is ticked; task receipts never drive task selection or any gate. Running now is a machine-wide process count, not an identified count of sessions in this project. A one-time page notice and a once-per-version session-start line announce the change; only their delivery flags are stored in `<data root>/state/notices.json`.

## Where your data goes

The data folder can be relocated through `fnl-setup`; the fixed pointer `~/.finolabs/vibecode/root.json` contains its absolute `root` path and a random `id` matching the new folder's `.root-id`.

The skills run inside a host agent such as Claude Code or Codex, which processes your conversation under its provider's policy. When you follow the delegation skills and delegate work to another agent (for example Codex or Antigravity), the brief, the files that agent reads and anything it produces are processed by that agent's provider under that provider's terms. Delegate only work over files you are allowed to share with that provider.

When the user has recorded a judge and the instruction check is on, `fnl-setup` Check can send instruction-file lines to the judge through the user's own evaluator skill: line text only, with a size cap, lines with a secret or machine-path hit dropped, nothing from a file with a secret finding, and never `.bak-*` backups, scan results or `CLAUDE.local.md`; the user consented to the judge separately.

## Update check

The update check is **on by default**, separate from usage metrics and their consent. At startup on Claude Code and Codex, a detached worker makes one HTTPS GET to `https://api.github.com/repos/finolabs/finolabs-vibecode/releases/latest` when the cache is missing or at least 24 hours old. It uses only the generic User-Agent `finolabs-vibecode-update-check`: no request body, credentials, cookies, username, machine, repository, session, installed version, prompts, code, paths or usage events. It sends nothing about the user. GitHub necessarily sees your connection's source IP. There are no redirects, proxies or retries.

Set `FNL_UPDATE_CHECK=off` in your host's environment to stop requests and notices. A “never ask” choice suppresses notices while checking continues. A “skip this version” choice suppresses only that version. The checker never updates the plugin; `fnl-update` asks for your clear yes before a native host update. Host-native updates have their own network behavior.

The resolved data root's `state/` folder (normally `~/.finolabs/vibecode/state/`, without environment overrides) holds `update-check.json` with only `checked_at` (Unix timestamp) and `tag` (validated stable release tag), plus `update-state.json` with only `skipped` (versions) and `never_ask` (boolean). Both are mode `0600`. No response body or error text is stored. These files are separate from usage events and metrics consent; turning metrics off or purging them does not stop the update check. Turning the update check off leaves existing files unchanged.

The first stable release carrying the checker gives no notice of itself: older installs have no checker, and an equal version produces no notice. Missing caches initialize silently; failures print nothing and never stop a session. See the [update-check spec](docs/specs/update-check.md) for the exact data and limits.

## Quota probe

For the quota probe, the plugin itself makes no network call. The user's own `agy`, `claude` and `codex` programs contact their providers with the user's own accounts; the plugin sends nothing about the user. This is separate from the update check above.

The probe stays off until setup records the dated opt-in in the canonical `<data root>/host.md`, under `## Quota probe`. That section lists selected agents, confirmed absolute executable and interpreter paths, and labelled Claude config folders. For the default Claude Code install, `CLAUDE_CONFIG_DIR` is left unset so the program resolves its own folder and login; it is set only to config folders the user listed. Each Claude install starts with its usual configuration, including hooks, plugins and servers. `FNL_QUOTA_PROBE=off` stops probing; metrics consent neither enables nor disables it.

`<data root>/state/quota/quota.json` stores, per agent and user-chosen label, only `measured`, `source` and groups with `name`, `window`, `remaining_fraction` and `reset_time`. It contains no account, identity, email, path, plan, credit or token fields. `backoff.json` stores only `retry_after` and an error class per agent and label; `worker.json` holds a random nonce and heartbeat while a worker runs. Files are private (0600) in a private folder (0700). No raw program output is saved. Successful readings wait 4 hours; failures wait at least 30 minutes, changed formats 24 hours, and Claude replies treated as prompts 7 days. The commands run from an empty private folder under `<data root>/tmp/`, removed afterwards. Turning probing off leaves cached files unchanged; delete the quota state to clear it. Hook-started worker survival after session end, other Claude text formats and Windows remain unverified.

## What the plugin stores on your machine

- With the auto gate enabled, `<data root>/state/auto-gate/<key>.json`: a repository key in the filename (the first 12 hex characters of SHA-256 of the normalized repository root), `decision` (`handoff` or `keep`) with `decided`, and optionally `denied`, both ISO timestamps. Before a decision, the file can contain only `denied`. The script stores no path, task label or session id and sends nothing over the network. This local-only state is independent of usage metrics. The account home comes from the operating system, never `HOME`, `FNL_STATE_DIR` or `XDG_STATE_HOME`. The hook uses an 8-hour window; stale state can be replaced on the next write, not automatically purged. Turning the gate off leaves existing files unchanged; delete them to clear the state.

- `<data root>/ledger.jsonl` (no environment override): one line per delegated run with a short task label, the agent, the model, timings and the outcome. It holds no prompts, code, secrets or personal data. Delete the file to clear it.
- Only after you consent in `fnl-setup`, through the plugin's hooks on Claude Code and Codex, and on Antigravity when you add its hook in setup: usage events in `<data root>/state/events-YYYY-MM.jsonl` (or under `FNL_STATE_DIR`, or in the older `${XDG_STATE_HOME:-~/.local/state}/finolabs-vibecode` folder where it already exists), one line per event. A line holds a time, a session id, a short code derived from the repository path, and a few fixed fields: the name of an `fnl-` skill or agent that ran, the coding router's depth, a review verdict with a pull request number, the number of tasks a coordinator kept with a fixed reason and who settled it, a task id (`task` event, only `id` of the form `T` plus one to four ASCII digits, nothing else), or the delegated run id (`dispatch`, the value of `FNL_DISPATCH_ID` or null, not a boolean). It never holds prompts, code, command text, file paths or review text. Judge receipts hold only `site`, `grader`, `result`, and `followed` from fixed enumerations; they never hold a question, an answer, a cost, a file name or a path. Consent always lives in `<data root>/state/consent.json` (the date and how long to keep events), ignoring environment overrides; an invalid root pointer disables consent. The events folder holds a marker file per session, an error counter with the class name of the latest error (never its text), and the dashboard (`dashboard.html`, its local `dashboard.js` and `data.js`), which `fnl-status` opens in your browser from your disk. Events older than the retention you chose (30, 90 or 365 days) are deleted at the start of a session, and `fnl-status purge` deletes them all at once. Set `FNL_METRICS=off`, or ask `fnl-status` to withdraw consent, to stop recording at any time; it asks you first, then runs `refresh.py consent --revoke --yes`. Task events are advisory dashboard data only and never drive task selection or a gate; any session can forge one. The events are best effort: they are read from tool calls and command text, so they can miss an action or count one that was only written out.
- `.finolabs/` in your repository (older versions used `.orchestration/`), when you follow `fnl-delegate` "Where files go": briefs, logs and handover notes that you or your agents write. The skill tells agents to keep this folder out of git.
- The host config file you create from `skills/fnl-delegate/references/host-template.md`, at a path you choose.

## Reporting issues

Public issues and pull requests are visible to everyone. Remove credentials, personal data and private repository content from any transcript, brief or log before you post it. Report security problems privately as described in [SECURITY.md](SECURITY.md).
