# Checks: where a repository's checks run and what they cost (release 0.2.4)

Status: implemented; for release 0.2.4, the owner settled the direction and the name on 2026-11-10. Built: items 1 to 7 (`checks.py` with `usage`, the shared reader `checks_list.py` with the document-only rule, the pre-push hook installer, the workflow writer `checks_setup.py ci`, `checks`' `references/ci.md` and the local receipt in `merge_check.py`).
For release 0.2.5 the list moved into each repository's own folder, and the `host.md` list is no longer read (owner decisions, 2026-11-11; "Storage" below); built.

## Why

Most people who build with coding agents keep their code on a hosted git service on a free plan, and a private repository's CI minutes run out (on a free plan GitHub gives 2,000 minutes a month and GitLab 400, by the providers' published plans as the owner's tooling recalled them; check the current plan before relying on a number). This plugin's own repository used 518 minutes in 110 runs in the 24 hours before this spec was written, every push running the whole suite of about 1,550 tests for 4 to 5 minutes, including pull requests that changed only documents. At that pace a free private plan lasts about four days.

The plugin already proves work locally (`verification`, now checks: targeted tests, `select_tests.py`, receipts, `heavy_run.py`), but a user who does not know how to set up local checks has nothing that does it for them, nothing that makes their cloud CI cheaper, and nothing that says plainly what happens when the minutes are gone.

## Owner decisions (2026-11-10)

- No CI system of our own and no runner. Running CI is what hosted CI, `act` (runs GitHub Actions workflows locally in containers) and hook managers such as `pre-commit` and `lefthook` already do; the plugin points to them and owns the decision: which checks, where they run, and what the merge gate may trust. A self-hosted runner is never set up by the plugin: on a public repository a pull request from a fork could run code on the user's machine.
- Extend the existing skill rather than add one: a new skill would put one more description into every session and compete for the same triggers ("run the tests", "CI is red", "CI minutes").
- The skill `verification` is renamed checks, the name the user meets in `/setup add checks` and `checks.py`. `verification` stays as a thin alias through 0.2.x, user-invoked only so it never competes for model triggers, and is removed in 0.3.0.

## What ships

1. **The rename.** `skills/checks` holds the content of `skills/verification`, its scripts and their copy groups; every reference in the plugin names checks; `skills/verification/SKILL.md` becomes a thin alias naming checks as its dependency, as `ask` does for `help`. The `description` gains the CI triggers and gets a trigger check. Scripts other skills copy keep their file names, so only paths and copy groups change.
2. **A check list per repository.** `/setup add checks` (a setup feature, `references/features/checks.md`) reads what the repository already has, without running it: scripts in `package.json`, the Python test runner it declares (pytest only from a declared dependency or pytest configuration, unittest only from a test module that imports it, otherwise skipped as "test runner not declared"), `Makefile` targets. The `run:` steps of its CI workflows are evidence, not checks: it lists each step's first line (at most 120 characters, with the job name when plainly readable) under `found in CI, add with --check if you want it` and converts none, because hand-parsing YAML into commands kept missing structures (folded scalars, step sequences, working directories); the agent or the user proposes any of them as a `--check "<name>=<JSON array>"` item, which preview validates like any other. The plugin never runs a stored array through a shell itself. It also refuses, as a best-effort guard and not a sandbox, an array whose program is a shell or a known launcher of another program (`env`, `xargs`, `sudo`, `timeout` and the like) or an interpreter given inline code; such a list can never be complete (a program may start a shell by itself, as `npm run` and `find -exec` do), and every check runs the repository's own code anyway. The protection that holds is that the user reads and approves each array in the preview, and that a repository cannot change which commands run; the preview says so plainly. It proposes an ordered list of checks, each a fixed command the user can read, shows it, and writes it only after a neutral yes; the commands still run the repository's own code, as cloud CI does, so the user runs the checks only on code they are willing to run. At most 20 checks of at most 1 KB each, names from a closed character set; a command is an argument list, never run through a shell. Only `checks_setup.py` (preview, digest, apply, as `levels_setup.py` does) writes it. Where it is stored: "Storage" below.
3. **One command.** `checks.py run [--changed] [--base <ref>]` runs the stored list in order through `heavy_run.py`, stops at the first failure and prints which check failed. `--changed` keeps only the checks whose scope the change touches, using `select_tests.py` for Python test modules and running the rest whole. It never edits files and makes no network call. `checks.py show` prints the list.
4. **An optional pre-push hook.** Setup offers, as its own neutral question, to install a git `pre-push` hook that runs `checks.py run --changed`. The installer resolves where Git really reads hooks (`git rev-parse --git-path hooks`), so a linked worktree gets the main repository's hooks folder, and the preview names that folder and says the hook then applies to every worktree of the repository. When `core.hooksPath` is set, the installer refuses and says so, and never changes that setting. It is the user's own git hook, not a plugin hook: it is installed and removed by a script with a preview and a backup, and an existing hook is never overwritten without a second yes. `git push --no-verify` still bypasses it, and setup says so.
5. **A cheaper cloud workflow.** `references/ci.md` in checks describes, and setup can write after a previewed yes, a workflow that runs on pull requests rather than every push, cancels a run superseded by a newer push (`concurrency` with `cancel-in-progress`), skips changes that touch only documents (`paths-ignore`), caches dependencies, and runs the whole suite on a schedule rather than on every change. Writing CI configuration is a shared repository setting, so it is never done during an away lease (a stop category in `docs/specs/away-decisions.md`).
6. **What the minutes cost.** `checks.py usage --from <file>` summarises runs, minutes and the share spent on document-only changes from a JSON file the agent produced with the host's own command (for GitHub, `gh run list --json`), so the script itself makes no network call. The plan's limit is a number the user gives in setup; the plugin never assumes one.
7. **When cloud CI cannot run.** Setup offers, per repository and as its own neutral question with what could go wrong stated, a mode where a passing `checks.py run` writes a local receipt. The receipt is written only by a run of the whole stored list (never `--changed`), only when the working tree is clean and the head is the same before and after the run (the checks `verify_claim.py` already makes), and it records the repository code, the head and the digest of the list that ran. The latest full run decides: a run of the whole list removes any earlier receipt before its first check, so a failed rerun leaves none; a `--changed` run neither writes nor removes one. `merge_check.py` consults it only when the checkout's `origin` remote names the `--repo` repository, accepts it only when all three match the pull request's head and the current list, and otherwise blocks as today; it then reports `checks: local receipt (<head>)` instead of `checks: all passed`; with the mode off, a missing cloud check still blocks as today. The receipt proves only that the user's machine ran the list at that head; it is self-reported, so the mode is meant for a repository one person works on, and setup says that it gives a reviewer nothing they can check.

## Owner decision (2026-11-11): the list is project-scoped

A repository's check list is project-scoped data and no longer lives in the shared `host.md`, which grew with every repository and which agents read before dispatching. It moves into the project's own folder, mirroring the user-scope layout: user scope is `~/.finolabs/vibecode/` (the data root), project scope is `<repository>/.finolabs/vibecode/`. Because the file now sits inside the repository's folder, an approved digest held in user scope keeps the rule that a pull request cannot change which commands run. Built for release 0.2.5.

## Owner decision (2026-11-11): no legacy fallback

The project file is the only store. Two review rounds showed that keeping the `## Checks` section of `host.md` as a fallback beside it kept reviving the old list, so the fallback, the `migrate` command and the record that marked a removed list are dropped rather than guarded. This is a breaking change for lists saved with 0.2.4: they are no longer read, and the 0.2.5 upgrade note asks the user to run `/setup add checks` again in each repository and then delete the old section from `host.md` by hand. Built for release 0.2.5.

## Storage

- **The file.** `<main checkout root>/.finolabs/vibecode/checks.json`, one per repository; linked worktrees share the main checkout's file, resolved the way `project_progress.repository_code` resolves identity, without running git. Folders are created 0700 and the file 0600; it is opened with no-follow descent from the filesystem root, owner-checked, size-bounded (64 KiB) and written atomically, and a link anywhere on the path is refused.
- **The schema.** Closed: `{"version": 1, "checks": [{"name": ..., "argv": [...]}], "local_receipt": true|false}`, in stored order. Names, limits and the shell, launcher and inline-code refusal are those of `check_argv` and the name rule. Unknown keys, a duplicate key, a wrong version or any refused entry make the file invalid, which reads as unset for that repository only and is never repaired on read.
- **The approval.** Apply records the SHA-256 of the exact file bytes and the time in `<data root>/state/checks-approved/<repository code>.json` (private state rules). The shared reader `checks_list.py` (four identical copies) reads the file only while its bytes match that digest; a file edited after approval, committed or checked out on a branch, or with no approval reads as unset with the reason `changed since it was approved`: nothing runs, the receipt mode is off, and the output says to run `/setup add checks` again.
- **Readers.** `checks_for(code, root)`, `receipt_mode(code, root)` and `receipt_status(code, head, root)` require the repository root from the caller (`checks.py`, `checks_setup.py`, and `merge_check.py` from the checkout it runs in); `list_digest` is unchanged. No file reads as `no entry` with the receipt mode off; a file without an approval or with a mismatching one reads as `changed since it was approved`, mode off; an invalid or unreadable file reads as unset with that reason.
- **The writer.** `checks_setup.py` `preview`, `apply`, `show`, `remove` and `receipt on|off` target the file and its approval and never open `host.md`. A save over a missing file starts with the receipt mode off and over an approved file keeps its mode; `receipt on|off` with no file refuses with "save a list first". When `.finolabs/` is missing from the repository's `.git/info/exclude` (the git common folder's), the preview says so and apply adds that one line, never to a tracked `.gitignore`; if that line cannot be added, apply says the file was saved and asks the user to add it.
  The preview binds the previous file's hash or its absence; replacing a file keeps the previous one as `checks.json.bak-<date>` beside it, 0600. Undo is `remove` for this repository: it deletes the file and its approval and leaves the backups, and a stale remove preview refuses before anything changes.
- **Lists saved with 0.2.4.** A `## Checks` section left in `host.md` is never read, whether or not it turned the receipt mode on, and nothing in the plugin writes or removes it; the user deletes it by hand.

## Dispatch receipts (2026-11-11)

Ledger data showed most delegated acceptances using `--accept-unverified`, because `checks.py run` wrote only the merge gate's local receipt (`state/checks-receipts/<code>.json`, opt-in) while `ledger.py finish --outcome accepted` reads `record.py`'s per-dispatch verification receipt (`state/verification/<id>.json`). `checks.py run --dispatch <id>` closes that gap: in the task checkout, a whole-list pass on a clean tree whose head and list did not move writes the verification receipt for that checkout and head, whatever the local-receipt mode; every such run first removes the dispatch's earlier receipt. The ledger's lookup is unchanged. `delegate`'s `references/accept.md` makes it the accept path where a list is approved, `verify_claim.py` over the brief's tests where none is, and keeps `--accept-unverified` for work with nothing to check. Covered by `tests/test_checks.py` (accepted by a real `ledger.py finish`, a linked worktree bound to itself, failed, dirty and moved runs, refusals).

## What enforces what

- Scripts: `checks_setup.py` for the stored list, its argument form, the preview and digest before any write, the approved digest and the exclude line; `checks_list.py` reading a project file only while it matches its approval; `heavy_run.py` serialising heavy checks; `checks.py` refusing a receipt on a dirty tree, a moved head or a narrowed run; `merge_check.py` matching repository, head and list digest and naming a local receipt as such; the hook installer resolving the hook folder and refusing a custom hooks path.
- The user's own git hook (when installed): running the checks before a push.
- Agent judgment, advisory: choosing what goes into the list, offering the cheaper workflow, running `checks.py run` before a push when no hook is installed.

## Limits

- A list built from a repository's files can miss a check the CI runs through a reusable action or a service container; the preview names every source it read so the user can add what is missing.
- A local pass on one machine does not prove the same result on another operating system.
- The plugin does not read a hosted plan's billing; it counts minutes from runs the user can already list.

## Evidence

Covered by `tests/test_checks.py`, `tests/test_checks_setup.py` and `tests/test_merge_check.py`.
The 0.2.5 storage move was built test first: two repositories keeping separate files with `remove` touching one, a linked worktree using the main checkout's file, an invalid file unset for its repository only, a symlinked file or folder refused, the exclude line added once and never to `.gitignore`, a file edited after approval, committed on a branch or without approval running nothing with the receipt mode off, and the receipt mode and `merge_check.py` reading the file.
Dropping the fallback was built test first too: a `## Checks` section left in `host.md` never read, with or without `local-receipt = on` (no checks, mode off, `merge_check.py` not satisfied by an old receipt), a save over a missing file beside such a section starting with the mode off, `host.md` byte-identical after save, receipt on and off, and remove, a stale remove preview changing nothing, and no `migrate` command.
A real `git push` through an installed hook and a run of the generated workflow on GitHub Actions remain unverified. The behaviors a build needed a red test for: the rename and the alias (counts, map, copy groups), list detection from each source without running anything, the stored argument form and its refusal of shell strings, preview and digest before any write, existing project settings reading and writing unchanged beside `## Checks`, `checks.py run` order, stop on failure and `--changed`, the hook install and removal with backup and no silent overwrite, a linked worktree resolving to the shared hooks folder, a refusal when `core.hooksPath` is set, the workflow writer's preview, `usage` from a fixture file, the local receipt refused on a dirty tree, a changed head or a `--changed` run, `merge_check.py` accepting it only for a matching repository, head and list digest and reporting it, and the mode off by default.
