# Release 0.2.5: scope

Status: in progress; all five packages are built on the main line or a branch for review; a real upgrade from 0.2.4 on a user's machine remains unverified.

## Rule (owner decisions, 2026-11-11)

User-scope data lives in the data root, `~/.finolabs/vibecode/` by default. Project-scope data lives at the same relative path inside the project, `<main checkout>/.finolabs/vibecode/`, shared by linked worktrees. Per-repository data does not belong in the shared `host.md`, which every agent reads before dispatching. A file inside the repository counts only while its exact bytes match a SHA-256 approved in the data root's private state folder, so a branch or a pull request cannot change what it says.

## What enforces what

- Scripts: `project_store.py` (shared copies registered in CI) for the identity, the project folder's no-follow, owner-checked reads, the closed schema, the approval and the exclude line; `project_progress.py` for the setters, the consent rule for `ledger` and `tasks`, and the readers; `parallel_slots.py` for the capacity reader; `checks_list.py` and `checks_setup.py` for the check list.
- Package 4: `check-references.py` (an alias folder holds only `SKILL.md` and loads the skill beside it; an older `fnl-` skill name appears only in the changelog, this spec or a line about the alias), the CI name check (folder equals `name`; an `fnl-` folder needs its skill beside it), `tests/test_manifests.py` (skill counts from the current folders, aliases counted apart, every alias thin and user-only with the target's argument hint), `fnl_metrics.py` and the metrics hook (closed list of skill names, old names mapped), and `merge_check.py` (`review-gate` or its older name adopts the gate).
  Whether an alias that loads another skill is followed by every host is agent judgment, advisory.
- Agent judgment, advisory: telling the user to set settings and labels again after the upgrade, deleting the old `host.md` sections by hand, and asking the yes before `settings --reset` with its preview that every project setting is discarded.

## Breaking changes and the upgrade

Settings, labels and check lists saved in `host.md` with 0.2.4 or earlier are no longer read. The 0.2.5 upgrade notes in `update` ask the user to run `/setup add checks`, `/setup add project` or `/setup add delegation` again in each repository where they changed something, then delete `## Checks`, `## Project settings`, `## Project labels` and the global `Ledger project:` and `Task file:` lines from `host.md` by hand. Never configured means the safe defaults: no checks with the receipt mode off, `parallel` 3 with no caps, the folder name as ledger name, no task file and the registered folder name as label.

Package 4 is breaking for anyone who typed or referenced the old names in their own files; the aliases keep typing and those references working, and the 0.2.5 upgrade note (`0.2.5/skill-names`) says so. On Claude Code `/help` and `/status` are host commands, so the documentation writes `/finolabs-vibecode:help` and `/finolabs-vibecode:status`, and the metrics hook does not count a bare typed `/help` or `/status`.

## Limits

- The dashboard shows a user label only for the repository it runs in; other repositories show their registered folder name, because their settings live in their own folders.
- `fnl_metrics.repo_code`, the metrics identity, is not changed by this release; for a real repository and a real linked worktree it gives the same code. It still accepts nonreciprocal worktree metadata, so a crafted `.git` file can attribute metrics events to another repository's code; validating it like `project_store.layout` is deferred to a later release (security review finding 4 on the 0.2.5 pull request). It selects no settings, checks or limits.
- A missing approval record in `<data root>/state/settings-approved/` reads as never configured, so its repository returns to the defaults (owner decision, 2026-11-11). Loss of private data-root state is outside the threat model: whoever can write the data root can also write an approval that matches any settings file, so a separate configured marker there would stop no one. Recovery from a broken file stays the explicit `project_progress.py settings --reset` (round 2 security review, finding 1).
- Package 4: which other host commands share a skill's short name was checked only for Claude Code's `/help` and `/status`; Codex invokes skills with `$`, and Antigravity's built-in commands are unverified. Released changelog entries and retired names keep their `fnl-` names as written; current specs use the new names.

## Evidence

Built test first. Package 2: a real `git worktree add` keeps the main checkout's code; a reciprocal layout without git keeps it; a mismatched back-pointer and fake metadata folders (inside the checkout, beside it, or naming another repository's common folder) fall back to the own root; such a checkout cannot read another repository's approved check list; a reciprocal pair under a common folder not named `.git` keeps its own code, settings, check list, receipt mode off and writes no exclude line elsewhere; group- or world-writable metadata files and folders fall back to the own root. Package 3: two repositories keep separate files; a linked worktree uses the main checkout's file; `## Project settings`, `## Project labels` and the global lines left in `host.md` are never read; an unapproved or branch-supplied file cannot raise `parallel` or redirect `tasks`; an approved file that gains a byte, is deleted, unreadable, unsafe or approved but malformed makes capacity unknown (exit 3, never available) and the ledger join unknown, never joined under the folder name; with the file modified or missing, `label --set`, `settings --set tasks=...` and `settings --set parallel=...` each refuse and leave capacity unknown, and `settings --reset` then a fresh set works; one progress collection reads the settings once; checkup reports broken settings as needing setup again without the folder-name guess; `host.md` stays byte-identical after every setter; the defaults hold when nothing is set; the session-start line and the dashboard work with no repository root and with an unset file. Covered by `tests/test_project_progress.py`, `tests/test_parallel_slots.py`, `tests/test_checks_setup.py`, `tests/test_refresh.py`, `tests/test_session_start.py` and `tests/test_checkup.py`.
