# Ledger

Record every dispatch with `scripts/ledger.py` in this skill's base directory. It appends to `ledger.jsonl` under the resolved data root, ignoring environment overrides and legacy folders. The ledger measures whether this routing works, so write each line at the moment it happens:

```bash
L="<this skill's base directory>/scripts/ledger.py"
python3 -I "$L" start --project demo-app --task "003 T101" \
  --kind implement --grade medium --coordinator claude --agent codex \
  --model gpt-6.1-sol --route-by table --budget 45
python3 -I "$L" finish <id> --outcome accepted --rework-rounds 1 --tests passed
python3 -I "$L" open                     # dispatches with no finish line
python3 -I "$L" stale                    # preview this repository's open records past 2x budget and 24 hours
python3 -I "$L" stale --close --digest <first 12+ hex digits>
python3 -I "$L" summary --since 2026-11-01
python3 -I "$L" summary --json           # the same rows as JSON, with quota and error counts
```

**Project label.** Choose one short, stable `--project` label per repository and use it from every worktree of that repository; never use a customer, personal or machine name. The dashboard joins dispatches to a repository by the repository's `ledger` project setting (the legacy `Ledger project:` line, then the folder name), not by its display label, so use that name; a different label joins nothing on the dashboard until `/setup add project` records it as the repository's `ledger` entry.

For review routing, the coordinator adds `--head <implementation head SHA>` to `finish`. This validates a forty-character lowercase SHA and copies the agent from the dispatch's start record; legacy records without a head cannot establish authorship. Commit trailers alone are insufficient. When acceptance uses a verification receipt, this head must also match the verified head. On a `review` dispatch, `--head` records `reviewed_head` instead, which never binds authorship.

A `review` dispatch is accepted on its posted review: `finish <id> --outcome accepted --head <reviewed head> --review-url <comment URL>` needs no receipt and no `--accept-unverified`. The URL must match `https://github.com/<owner>/<repo>/pull/<n>#issuecomment-<id>`; it is checked by pattern, never fetched or stored, and the line records `review_posted: true`. Every other kind keeps the receipt rule. `--reason <text>` may go with any outcome; only its digest is stored.

`start` prints the dispatch id on stdout and, on stderr, the run's name as `label: <runner>: <project> <task>`, where the runner is the family plus the short model name (`codex sol`, `agy flash`, `claude opus`); `--task` holds only scope and activity. `start` records optional `coord_session`: the first 12 hex characters of the SHA-256 of the `CLAUDE_CODE_SESSION_ID` environment value, never the raw id and never from a command-line option (an argument would show in process listings and parser errors). It is `null` when the variable is unset or unusable, and older lines without it remain readable. It is a correlation identifier, not protection: a predictable id can be guessed from its hash, so treat the ledger as private.

Before `finish --outcome accepted`, get the receipt as [accept.md](accept.md) says: `checks`' `checks.py run --dispatch <id>` in the task checkout when the repository has an approved check list, else the self-contained `verify_claim.py` from `checks` "Accepting someone else's work", and read its evidence. Pass `--checkout <task checkout>` to both `start` and `finish` when the task runs elsewhere: the gate requires a passing receipt for that checkout and its current head. For work with nothing to check, the coordinator can use `--accept-unverified --reason <text>`; keep the full reason in the coordinator report because the ledger stores only its SHA-256 digest and counts the exception in `summary`.

`--grade` is one of `easy`, `medium`, `hard`, `very-hard` and `ultra-hard` (`SKILL.md` "Grade" defines them); lines written before `ultra-hard` existed still read.

`start` also takes optional `--install <name>` (an extra Claude Code command such as `claudework`, the names the assignment matrix accepts), `--work-type <type>` (`frontend`, `design`, `video`, `three-d`, `image-generation`, `transcription`) and `--level <1-5>` (the grade's number). With a type and a level it runs the same query as `route_pick.py pick` and records `pick_rank`: the 1-based position of the chosen install (else agent) and model among the survivors, or 0 outside them. On stderr, before the label, it prints `off the preferred order: rank <n>` above 1 or `off the preferred set: <reason>` at 0. It never refuses the dispatch; with no preference, no usable matrix or a failed pick, the rank is left out. `summary` then adds, per install or agent, the shares at rank 1, at a lower rank and outside the set, counted only over dispatches with a `pick_rank`, and how many were left out; `--json` is unchanged.

Record why a route was taken: `--reason fallback-quota` for a quota fallback, `--reason fallback-failure` for a reroute after a failed run, `--reason user-choice --route-by user` for a route the user named, and `--route-by judge` when a validated configured-judge response informed it.

Under Delegation mode `manual`, `start` refuses a cross-family record without `--route-by user`, writes nothing and exits 1. Claude, `claude-session` and `subagent` are the Claude family; own-family records remain allowed. This check blocks the record, not the dispatch itself; an unavailable or invalid mode leaves the previous behavior unchanged.

`--agent claude-session` records a Claude Code app or interactive session, `claude` a headless `claude -p` run, `subagent` an in-session subagent. Task labels are short names; the ledger holds no task data, secrets or personal data. `summary` reports, per agent, model, kind and grade, the first-pass acceptance rate, timeouts and stalls, fallbacks, median duration, unverified acceptances and the quota, error and cancelled counts; `--json` adds `closed_late`, `retro`, `accepted_findings` and `review_unposted`. A `cancelled` record closed late (its note starts with `closed late by ledger stale` or `closed late by the coordinator`) gives no verdict on the run, so it stays out of the counts, rates and medians and is shown as a separate total. Below the table, `summary` flags accepted runs whose log scan had findings and review acceptances recorded without `--review-url`.

For task progress, use labels of the form `<feature> T<id>` (for example `003 T012`); include the exact three-digit feature number. Multiple ids or ranges of at most 20 ids link each task; labels without a feature remain unlinked. The rest of the label is discarded by the dashboard.

`finish` accepts `--log-path <log>` directly inside the private `.finolabs/logs/` folder of the current checkout, of the `--checkout` checkout or of the main checkout (the parent of git's common dir); it scans before recording and stores only `log_scan: no_findings|findings|not_scanned`. An empty log is `not_scanned`. Any other location, a link or another user's file is refused with one fixed reason line that names no path, and nothing is recorded. Omit the path to record `not_scanned`. The `--head` and verification-receipt gate still apply.

**Field checks.** `finish` refuses, writing nothing, a negative `--rework-rounds`, more than 2 rework rounds (the loop's limit) without a `--reason`, and `--outcome accepted` with `--tests failed`. `start` warns on stderr, after the label, and still records when the model is not one the assignment matrix lists, or when `--project` differs from the `ledger` entry of the repository's project settings; with no usable matrix or no such entry it says nothing. Dispatch ids are checked against the ledger under the finish lock, so two starts in the same second never share one. Use `finish --retro` for a record written after the fact (its start and finish lines written together); it records `retro: true`, and `summary` leaves its duration out of the medians.

**Ended runs.** When `delegate_env.py` runs a dispatch with `FNL_DISPATCH_ID` set to its ledger id, it appends `{"event": "ended", "id", "ts", "exit"}` after the child exits (a signal gives a negative code). It holds no command text, output or path, is written only when the ledger already exists, and a failed write is silent and never changes the wrapper's exit status (script-enforced). The line carries no outcome and is not a finish: `open` shows `ended exit=<n>` beside the record, `stale` treats it as due after 24 hours (or `--older-than-hours`) without waiting for twice its budget and proposes `error` for a nonzero exit or `cancelled` ("run ended exit 0; no verdict recorded") for exit 0, and `summary` ignores it.

**Open-run reminder.** On Claude Code a `UserPromptSubmit` hook (`scripts/open_dispatch_nudge.py`) prints one fixed line, at most once per 30 minutes per session, naming the count and up to five ids of runs this session started (`coord_session`) that have no `finish` line and either an `ended` line or an age past their budget (60 minutes when absent). It only prints, never denies, reads only the ledger and its own throttle mark, and `FNL_DISPATCH_NUDGE=off` disables it. Recording the outcome stays agent judgment (advisory); Codex and Antigravity are not covered.

**Stale records.** `stale` considers only this repository's records: those whose `project` equals the ledger project `status` resolves for the current checkout (its `ledger` project setting, else the checkout folder name). When none resolves it refuses. `--all-projects` widens the preview to every project and prints a warning that other projects' runs cannot be judged from this checkout; such a preview closes only with `stale --close --all-projects --digest <digest>`, and a one-project preview closes only from a checkout of that project. It lists the open records past the stale threshold: by default past twice the record's budget and at least 24 hours old (a record with no usable budget after 24 hours); `--older-than-hours <n>` (1 to 8760) sets another threshold, but a record still inside its budget is never listed. Each line shows the id, age against budget, the record's label (`<project>: <task>`) and what can be learned without reading a log's content: whether `<id>.log` exists in the private `.finolabs/logs/` folder of the current checkout, its last-write age and the `exit=<code>` line within its last 64 bytes. Each listed record gets an outcome: `error` for a nonzero exit line, `stalled` for exit 0 or no exit line, `cancelled` when no log exists; a log that is a symlink, hard link or another user's file is refused and its record left open. The preview writes nothing to the ledger; it saves the plan in the data root's private state folder and prints its SHA-256 digest, valid for 60 minutes. Show the list to the user and, after their yes, run `stale --close --digest <first 12+ hex digits>`: it writes one `finish` line per previewed record that is still open and still past the threshold the preview used, with a note saying it was closed late and `log_scan: not_scanned`, then removes the preview. A digest mismatch, an expired or missing preview, a changed data root or a changed scope writes nothing. Lines are only appended, under the same lock as `finish`; none is deleted. It never marks a record `accepted` and never touches verification receipts. `open`, `summary` and the session-start open count read the closing line like any `finish`. Enforcer: the digest check in `ledger.py`; asking the user before closing is agent judgment (advisory).
