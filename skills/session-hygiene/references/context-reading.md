# Context reading (Claude Code, Codex and Antigravity)

When the user configured the status-line recorder, run `python3 -I <this skill folder>/scripts/context_snapshot.py read --latest --host <claude|antigravity>` for the active host. Use `check --latest --host <host> --threshold <chosen tokens> --boundary <yes|no|unknown>` to feed those counts to the steward (advisory, agent judgment). Without a host, `--latest` reads whichever host wrote last.

A host filter can still select another parallel session of that host. Use `--latest` as your own reading only when the active session is unambiguous; otherwise use `--session <id> --host <host>` with your own id or say that your own reading is unavailable (advisory, agent judgment). Claude uses `session_id`; Antigravity uses `conversation_id`; Codex uses the thread id. Session lookups default to Claude when no host is given.

## Probe (Claude Code and Codex)

When no fresh snapshot of your own session exists, run `context_snapshot.py probe --host <claude|codex> --session <id>` once at a work boundary, then `check --session <id> --host <host> ...` (advisory, agent judgment). The id is the one on the session-start `Session id:` line; the hook prints it only for a lowercase UUID, and the probe refuses any other id. With more than one Claude config folder listed in the quota probe setup, add `--config <label>` for the install this session runs in. Never run the probe from a hook, a loop or a background worker, and never retry a refusal at once.

It runs only the program the user confirmed in the quota probe setup (`/setup add quota`): the same resolved, owner-checked executable, allowlisted environment, empty private working folder, 30-second limit that kills the process group and 64 KiB output cap. Without that confirmation, or with `FNL_CONTEXT_PROBE=off`, it refuses. Claude runs the fixed `claude -p /context --resume <id> --fork-session --no-session-persistence --output-format json`; the probe keeps only the `Tokens: <used> / <window>` line and refuses a reply that ran a model turn or cost anything. Codex runs `codex app-server`: a constant `initialize`, `initialized`, `thread/read` and `thread/goal/get`; it stops unless the thread is idle or not loaded, not archived and has no goal, then sends `thread/resume` with only the thread id and keeps `last.totalTokens` and `modelContextWindow` from the first `thread/tokenUsage/updated` for that thread. It never answers a server request and sends no turn. Output is the `read` JSON; any failure exits 3 with one fixed message. Antigravity is not covered.

Unverified: whether `claude -p --resume` finds a session from the probe's neutral working folder (the hand check ran it from an unrecorded folder; the rule requires a neutral folder, so a session the program cannot find there exits 3), Codex hook delivery of the thread id as `session_id`, and live behavior of a Codex thread with a goal.

The SessionStart Context line is Claude-only and always refers to the starting session, on every source except `compact`; it is only a reading at that time. There is no Antigravity SessionStart hook here.

Enforcer: `context_snapshot.py` validates bounded integer input, stores metadata privately and atomically, retains at most 20 snapshots across all hosts and enforces freshness (default one hour). `read`/`check` exit 3 with a fixed message when unavailable or stale. Their JSON output has no host key. Antigravity window zero means unknown and records nothing; null or invalid usage clears only that host's old reading. No transcript is read.

Setup offers each present host separate context-reading consent and preview approval (advisory, agent judgment); an enabled Antigravity compaction stop does not imply consent to this recorder. Without a reading, say so and never invent numbers (advisory, agent judgment). Antigravity's separate stop continues to use transcript bytes; live Antigravity status-line payloads and `invocationNum` reset semantics remain unverified.

Vendor documentation researched 07/11/2026: Claude Code [statusline](https://code.claude.com/docs/en/statusline.md) documents `context_window.current_usage` and window fields on stdin. The desktop app's Code tab behavior for `statusLine` is undocumented and unverified: the owner's desktop session recorded no snapshot while a terminal session did. Neither observation proves delivery in every session.

Antigravity [status-line docs](https://antigravity.google/docs/cli/statusline/), through 1.5.3 (07/11/2026), document stdin `context_window` (`context_window_size` 0 means unknown, `used_percentage`, `current_usage`), `conversation_id` and `transcript_path`; `statusLine` belongs in `~/.gemini/antigravity-cli/settings.json`. The host runs it at most every 300 ms, with a 5 s limit, disabling it after 30 consecutive failures. These are documented contracts; this plugin's live delivery remains unverified.

Codex 0.167.0 [app-server](https://learn.chatgpt.com/docs/app-server), [config reference](https://learn.chatgpt.com/docs/config-reference) and pinned `rust-v0.167.0` source (07/11/2026) expose context telemetry through `thread/tokenUsage/updated` (`tokenUsage.last.totalTokens`, `modelContextWindow`) and TUI built-ins `context-used`, `context-remaining`, `context-window-size`. There is no external status-line command receiving JSON, so this recorder does not cover Codex; the probe above reads the same telemetry. `notify` has no token fields; PostModelRequest has nullable `token_usage` without window size. `codex exec --json` reports execution usage, not a context snapshot; no standalone per-session usage command was found.
