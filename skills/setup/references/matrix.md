# Assignment matrix (part of `add delegation`)

Writes the canonical `## Assignment matrix` section: for each helper, which task levels it takes, which types of work suit it, which model to use and which reviews it owns, plus the judge. Questions follow [interview.md](interview.md): native question tool, neutral Yes and No, none preselected. Only the section is written (advisory: the script enforces the format and the write, not the choices).

Run `python3 -I <this skill folder>/scripts/matrix_setup.py candidates` first: names only, runs nothing, shows no path. Offer each name as a candidate; a shell function is never listed, so the user types its name.

Ask once per helper, in one pass, as free text; a blank answer skips that part:
1. Levels: "Which task levels can <helper> take? 1 easy to 5 ultra hard; answer like 3-5, blank for all five."
2. Types of work: "Which types of work suit <helper>? Choose from frontend, design, video, three-d, image-generation, transcription (at most four); blank for none." When several helpers list a type, the earlier one is preferred.
3. Model: "Which full model id should <helper> use for those types? Blank for its default." A model not allowed on this machine is kept and shown as unverified.
3a. Models by kind of work: "Should <helper> use different models for different kinds of work?" Blank or no skips it. With yes, ask for each rule in plain words, at most eight, in the order they should be tried (the first that fits wins): which model, for which kinds of work (implement, code-review, security-review, navigator, advisor), types (the list above) or levels (like 4-5), and an optional fallback model used only when the first is out of quota. Write each rule as `<model>[ then <fallback>] for <selector>, ...`, a level as `levels L-H`, and join the rules with ` | `. A rule that names no kind applies only to implementation work. Never add a rule, selector or fallback the user did not give; a fallback applies only to Antigravity, whose quota is read per model pool.
4. Roles: "Which roles does <helper> own? Choose from code-review, security-review, navigator, advisor (the optional agent asked for opinions and away decisions); each role goes to one helper; blank or none for no role."
Then ask the judge: "Who judges evidence: jev (TypeSafe, needs your own key and approval) or host (the small host model)?"
If the answer is jev, ask the separate TypeSafe consent question of [features/roles.md](features/roles.md) ("Judge"), with its Yes, No, Undo and Choices, before the save question below; pass `--judge jev` only after its own yes, otherwise `--judge host`. The save question never stands in for that consent.

Build one line per helper: `<agent>: levels L-H[; works on <type>, ...][; model <id>][; models <rule> | <rule> ...][; roles <role>, ...]`, keys in that order, with no leading dash. Example: `antigravity: levels 1-5; works on design, video; models gemini-4-argon-high then gemini-3.8-flash-high for security-review | gemini-4-hydrogen-high for design, video, levels 4-5 | gemini-3.8-flash-high for code-review; roles security-review`.
Preview: `python3 -I <this skill folder>/scripts/matrix_setup.py preview --judge <jev|host> --consent yes --line "<agent line>" ...` (repeat `--line`; `validate` takes the same options and prints without saving). Show the lines printed and the digest. Read the rules back to the user from the printed line, one per line in order, in plain words ("security reviews: gemini-4-argon-high, then gemini-3.8-flash-high when it is out of quota"), and confirm they match what the user said before the save question; `matrix_setup.py show` lists them the same way after the write (`Models <agent> <n>: <rule>`).
Ask: "Save this assignment matrix, and let task briefs and repository files go to the provider of each listed helper and the judge?"
Yes: Write the shown section in local host.md after a backup; the `Consent:` line records today's date. Saving sends nothing; later helper and judge work uses those providers.
No: Leave the file unchanged; ask later.
Undo: Preview a matrix with no agent lines and `--consent no`, or restore the backup.
Choices: "Yes, save the matrix" / "No, keep the current settings".
After a clear yes run `matrix_setup.py apply --digest <printed Digest prefix, at least 12 hex>`, then `matrix_setup.py show`; exit 0 alone proves nothing. The preview expires after 60 minutes and any change to host.md makes it stale.

Moving from the old sections: `matrix_setup.py migrate` previews a matrix built from `## Agent roles` and `## Agent levels` (roles become each helper's `roles`, a helper named only in roles shows `levels 1-5` to edit, levels carry over, the judge carries over). Every line it cannot map is printed as `dropped`; `apply` refuses (exit 3) until the user has read them and you add `--ack-dropped`. Consent is not inherited: when the carried judge is jev, first ask the TypeSafe question of [features/roles.md](features/roles.md) and on No do not apply the migration but run `preview --judge host` with the printed lines; then ask the question above again, and only after a clear yes add `--consent yes` to `apply`, which then removes both old sections in the same write. The backup keeps the originals. It refuses when the matrix already exists.

The matrix is the only source of review roles and the judge: `## Agent roles` is never read, so without a matrix no role is set and the judge is `host` (script-enforced). It is also the one path for levels: with a valid matrix the readers ignore `## Agent levels`, and `levels.md` serves only a user who declines the matrix.
