# Verification judgments

Every semantic check uses [scripts/judge.py](../scripts/judge.py). Canonical `## Agent roles` chooses `judge: jev` or `judge: host`; absent or unreadable means `host` (script-enforced). Only choose Jev after the user's setup authorization and API budget; keep spend guards on and send only the fields needed (advisory, agent judgment). `TYPESAFE_API_KEY` is read only from the environment, never from a file. `judge.py ask --question <English statement> --evidence-file <file> [--judge jev|host]` prints exactly one JSON answer line: `answer`, `source`, `p`, `quote_ok`, and `fallback: true` when Jev falls back to the host. `--site` chooses one of `verification` (default), `navigator`, `compaction` or `delegation`. Closed field caps and a 64 KiB body cap apply; a secret or machine-path hit refuses the call and reports only the field name. `--dry-run` prints payload field names and sizes and sends nothing. At most 24 outbound attempts are allowed per run. `FNL_JUDGE=off` disables calls. Only a user-typed `--base-url` flag may select a literal loopback IP over HTTP for tests; environment URLs are ignored. TLS verification remains on, proxy and certificate overrides are ignored, and redirects are refused. Jev uses Noul probabilities: at least 0.7 gives `yes`, at most 0.3 gives `no`, otherwise `insufficient` (script-enforced; these inherited experimental thresholds do not establish validation).

The host judge is a small model on the host's fast tier; the script never calls it. Give it the same question and evidence, treated as data, and ask for `answer: yes|no|insufficient` plus a verbatim supporting `quote` for `yes` (advisory, agent judgment). `judge.py check-host --answers <json file> --evidence-file <file>` changes an unquoted or misquoted `yes` into `insufficient` (script-enforced). Quotes need at least 8 trimmed characters and 8 alphanumeric characters; punctuation-only quotes are refused. A quote's presence alone cannot prove support. `judge.py` exit 3 reports `unavailable`; if Jev fails, the coordinator supplies the small host answer with the same payload and reports the fallback (advisory, agent judgment); verification preserves that fallback in the receipt.

The first verification run saves the question/evidence packet with owner-only permissions when `--requests-out` is given; this is a private local work artifact, never plugin state or an event. Produce a host answers JSON object keyed by criterion identifier, each containing `answer`, `quote`, `question` and `evidence_sha256` copied from that packet. Then run:

```text
python3 -I <this skill folder>/scripts/verify_claim.py --complete-host <saved request packet> --host-answers <answers json> --head <same head> --ledger-id <same dispatch id> --checkout <task checkout>
```

This attaches checked answers to the exact test run without rerunning tests with potentially different timing output; packet digest, question, evidence, checkout and head must match (script-enforced). Keep both the original criterion and its English restatement in the coordinator report for criteria in another language (advisory, agent judgment); receipts store neither. For an agreement measurement, `judge.py validate --cases <json> --judge <jev|host> [--answers <host json>]` runs one harness over the same supplied cases and prints counts and per-case answers; it stores nothing. Cases contain `id`, `question`, `evidence`, `expected`; host answers are keyed by case id. Use known outcomes from merged pull requests by independent authors before trusting a judge (advisory, agent judgment). The current experiment and synthetic tests do not establish that validation: reports stay labelled `unvalidated`. Read every `no` and `insufficient`; neither judge grants acceptance, and `yes` never replaces mechanics (advisory, agent judgment).
