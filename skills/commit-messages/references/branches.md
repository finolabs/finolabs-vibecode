# Branches

The branch flow that `SKILL.md` "Branches" summarizes. Read it before creating, naming, syncing or merging a branch, resolving conflicts, cleaning up after a merge, or backporting a fix.

Trunk-based: the default branch stays releasable, and every change reaches it through a short-lived branch and a pull request. A branching scheme the repository already documents wins over this default.

- **Main checkout**: it stays on the default branch (the branch pull requests target, whatever its name) and clean: a read-only mirror to read the latest code from and cut worktrees from, never committed to. Never run `git switch` or `git checkout <branch>` there; every branch, a coordinator's own small fix included, gets a worktree of its own. Advisory (agent judgment); the session start warns when the main checkout is off its default branch.
- **Start**: commit on a branch of your own, in its own worktree. Fetch, then cut it from the tip of its base, the default branch or `release/X.Y` for a fix to an older line, under the repository's worktree folder (such as `.claude/worktrees/`): `git worktree add -b <name> <path> origin/<base>`. Parallel runs get one worktree and branch each (`delegate` "Parallel dispatch"); a feature has one implementing checkout (`delegate`'s `references/coordinator-sessions.md`, "Checkouts and writers").
- **Name**: `<type>/<task>` in lowercase kebab case, with a type from `feat`, `fix`, `docs`, `chore`, `refactor`, `hotfix`, and the task ID where the project tracks one (`fix/142-parser-null`). A branch the host names for its own worktree keeps that name.
- **Lifetime**: days, not weeks. Split a larger change into pull requests that each leave the base releasable.
- **Sync**: bring the base in before opening the pull request and whenever it changed the files you touch. A local branch you have not pushed yet: rebase onto `origin/<base>`. A pushed branch: merge the base into it, so its published history stays as others fetched it; rebasing it needs authority (`SKILL.md` "Authority") and then `git push --force-with-lease=<branch>:<sha> --force-if-includes`, where `<sha>` is the remote head you rebased from. Use the host's sync tool where it offers one for its worktrees.
- **Conflicts**: resolve them on the branch. Read both sides and keep each one's intent; where the intents contradict, stop and ask whoever owns the other change. Rerun the targeted tests (`checks`); the resolution is part of the change the reviews cover.
- **Default branch rules**: a ruleset or branch protection on the default branch is the merge path: changes arrive by pull request with its required checks and reviews, without an administrator bypass unless the owner allows one and records why (`open-source-review`). An agent never uses a bypass, even when its login holds one. A rejected direct push means: open a pull request.
- **Merge**: through the pull request, after the merge check (`review-gate` "Pull requests"), with a method the repository allows; prefer a merge commit, which keeps each commit as written. Pin the merge to the reviewed head so a later push cannot ride along: `gh pr merge <number> --merge --match-head-commit <sha>` on GitHub.
- **After merge**: whoever merged deletes the head branch on the forge (`--delete-branch`, or the repository's automatic deletion) only when that agent or its runs created it and no running session or run uses it. Remove only worktrees (`git worktree remove <path>`) and branches this agent or its runs created, and only when no running session or run uses them; delete a local branch with `git branch -d`, and use `-D` only with the owner's go.
- **Worktree sweep**: right after a successful merge, run `python3 -I <this skill's folder>/scripts/worktree_sweep.py list`. It is read-only and deletes nothing: for each linked worktree it prints the path (backslashes, control and non-ASCII characters escaped), branch, size, clean or dirty, unpushed, merged and a `candidate` flag (merged, clean, nothing unpushed, not locked, not detached, not the working folder, no nesting with another worktree), and under each candidate the two commands `git worktree remove -- <path>` (never `--force`) and `git branch -d -- <branch>`, each name quoted for a POSIX shell. Only for the worktree of the pull request just merged, when it is a candidate and this agent or its runs created it, run exactly those two commands; git refuses a dirty worktree and `-d` refuses an unmerged branch. `git worktree remove` also deletes the files git ignores inside that worktree. Leave every other worktree in place and tell the user the rest of the list with sizes, so their storage is not used up. Running the commands and choosing the worktree are advisory (agent judgment); git enforces its own checks. On Claude Code a hook prints a reminder after a successful `gh pr merge`. Worktrees of delegated runs need no manual step: `delegate`'s `ledger.py` removes them once merged (its `references/loop.md`, step 7).
- **Hotfix and backport**: fix on the default branch first, then for each supported older line cut a branch from `release/X.Y`, apply the fix with `git cherry-pick -x <sha>` and open its own pull request. A fix that applies only to the older line starts on that line. Create `release/X.Y` from the latest tag of that line (the highest `vX.Y.Z`) when an older line first needs a fix; tags follow `versioning` "Tags".
