# Check existing setup

1. Run `python3 -I <this skill folder>/scripts/checkup.py` from the repository being checked; `--json` gives the same evidence as JSON. Read every result. The script inspects files and PATH entries only, changes nothing, calls no host CLI and does not run the smoke task. A refused symlink or unknown installation layout stays unverified. An `ok` means that the named file evidence exists, not that the host obeys it.
2. For each host whose CLI is `ok` (or a PATH link is unverified), print a short table with these columns: **runs on its own / asks you first / does not happen here**. Put only observed facts in it. For example, say “SessionStart is declared; execution unverified”, never “the reminder runs”. If a column has no evidence, write “unverified”. An absent CLI or hook declaration proves only that specific absence. Cached versions do not prove an active installation. Neither a coding-router pointer nor a review line proves automatic enforcement. Hook trust, approval policy and compaction thresholds stay unverified until observed in that host. Do not infer consent to metrics, automatic delegation, reviews, commits or permission grants.
3. List each missing item with one next action. Use `/fnl-setup` section A for host config, B for local exclude, C for the Agent skills block or review adoption, and `/fnl-setup-instructions` for user instructions or their router pointer. For a missing CLI or plugin, use `/fnl-setup` Explore to obtain the host's current install command; do not invent one. For missing hook declarations, use `/fnl-setup` section F to inspect the installation and show any proposed change before consent. Use the skill command convention already stated by the host. List unverified items separately as limits, not failures; a file-only check cannot fix runtime uncertainty.
4. Offer one small smoke task the user can watch: “I can route a proposed one-line README correction, say the depth I chose and which checks I would run, without editing files.” If accepted, the agent runs that read-only task through `fnl-coding-router` and reports what actually happened; the script never executes it. This observes one routing decision, not hook execution or every future task. Observe any other host behavior only with a separate bounded task the user authorizes.

End plainly: “Auto is never 100%. Files show what is configured; a task you watch shows what actually runs.”
